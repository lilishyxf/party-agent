[样式3] 摘要
[Normal] 本设计文档是"基于 Dify 的高校党务 AI 平台设计开发"毕业设计项目的软件设计文档，对系统的功能划分、整体架构、部署形态、数据流向、数据库结构以及扩展模块的算法设计进行完整描述，作为后续软件实施阶段的设计依据。系统面向高校各级党支部的日常党务工作场景，以微信公众号作为党员日常入口，以开源应用编排平台 Dify 作为应用层底座，以党务 AI 大模型作为核心检索与生成引擎，覆盖学习、自测、写作、会议、发展党员、台账、系统管理七个通识功能模块。在通识模块之外，系统设计了面向"党员理论学习与教师专业课融合"场景的扩展模块——课程思政短视频脚本生成系统，该模块将党员应知应会的理论内容与教师的专业课教学内容相结合，在课程思政教学的六项原则约束下，生成可用于驱动视频生成引擎的脚本，产出教学短视频。系统在技术架构上采用"应用编排层与算法服务层解耦"的设计，使算法研究产出可独立评估、可单独迭代、可独立开源；在数据合规上以"数据不出校园"为最高约束，跨合规边界的数据流在架构层面显式标注并经脱敏处理。本文档覆盖系统的完整设计，通识模块的 P0 部分将在 5-6 月实施，扩展模块在设计阶段完整呈现、实施阶段精简验证。
[Normal] 关键词：党务管理；智能 Agent；检索增强生成；Dify；课程思政

[样式3] Abstract
[Normal] This document presents the software design for the graduation project "Design and Development of a University Party Affairs AI Platform Based on Dify." The system serves daily party affairs scenarios in university-level party branches, using a WeChat Official Account as the primary user interface, the open-source Dify platform as the application orchestration layer, and a self-developed algorithm service as the core retrieval and generation engine. It covers seven general-purpose modules including study, self-assessment, writing assistance, meetings, party member development, ledger management, and system administration. An extension module — a curriculum-based ideological education short video script generation system — is designed to align party theory with professional course content under six pedagogical principles, producing structured storyboard scripts for video generation. The system architecture decouples the application layer from the algorithm service layer, enabling independent evaluation and ablation experiments. Data compliance follows a strict "data stays on campus" policy with explicit boundary annotations across all design views.
[Normal] Key Words: party affairs management; intelligent agent; retrieval-augmented generation; Dify; curriculum-based ideological education

[2] 1.1 文档目的与范围
[Normal]     本文档是"基于 Dify 的高校 AI 党务平台设计开发"毕业设计项目的软件设计文档(V4),按照《西安工业大学毕业设计管理手册》撰写规范重新组织,对系统的功能划分、整体架构、部署形态、数据流向、数据库结构以及扩展模块的算法设计进行完整描述,作为后续软件实施阶段的设计依据。本文档的覆盖范围包含本平台的完整设计:面向党员日常使用的通识模块(学习、自测、写作、会议、发展党员、台账、系统管理)和面向"党员理论学习与教师专业课融合"场景的扩展模块(课程思政短视频脚本生成系统)。通识模块的 P0 部分将在 5-6 月实施,扩展模块的设计在本文档中完整呈现,实施阶段精简验证。

[2] 1.2 系统定位
[Normal]        基于Dify的高校AI党务平台 是一个面向高校各级党支部的 AI 党务工作助手。系统以微信公众号（服务号）作为面向党员的日常入口，以 Dify 作为开发平台，以党务AI大模型作为核心检索与生成引擎，服务于支部书记、支部委员与普通党员的日常党务工作，核心覆盖学习、自测、写作三类高频场景，并在 P1、P2 阶段逐步扩展会议、发展党员、台账等场景。
[Normal]       本系统立足于实际应用，核心用 AI 大模型与自动化技术，实现党务管理、党员教育、组织建设，常见形态为私有化部署 + 党建专属知识库 + 智能应用模块。依托党建专属大模型实现智能文稿生成、政策智能问答、内容合规风控、党建数据分析；结合 RPA 流程自动化完成党务流程流转、台账报表自动生成、会议全流程闭环、任务智能督办，全面实现党务工作智能化、标准化、轻量化。通过知识管理，实现党务工作与具体业务结合的创新，将时政理论与教师日常教学、课堂育人、师德师风、教研教改等实际工作深度融合、一体推进，做到以理论铸魂、以学习赋能、以实干践行初心使命，算法将在第 7 章独立展开。
[Normal] 
[Normal] 参考样式
[2] 1.3 设计原则
[Normal] a. 数据合规优先。 党务数据涉及党员档案、组织内部资料，属于"私密文件"范畴。系统在选型与部署的所有环节，均以"数据不出校园"为最高约束。所有可控组件部署在校园网内私有环境；无法在本地承载的大模型推理被独立成"外部模型层"，跨边界的数据流统一经过脱敏中间件处理。
[Normal] b. 应用与算法分层。 Dify 承担应用层职责(对话编排、知识库管理、工作流配置);党务 AI 大模型在算法服务层提供核心检索与生成能力,两者通过 HTTP API 通信。这一分层使得算法能力可独立迭代,同时不影响产品端的快速交付。
[Normal] c. 面向多角色与多入口。 系统同时服务党员（高频、日常使用）、支部书记（中频、管理使用）与教师（扩展模块使用）三类角色，因此在用户接入层划分了微信公众号（P0，党员）、Web 管理后台（P2，书记）与独立 Web 前端（扩展模块，教师）三个入口，而非把所有功能挤进单一终端。
[Normal] d. 为扩展模块预留接口。 通识模块与扩展模块在体系结构上共享算法服务层的基础能力，扩展模块在此基础上做研究方向的延伸，具体算法在第 7 章展开。设计上保证通识模块的部署形态可承载扩展模块的接入，不需要重构底层架构。
[Normal] 
[样式3] 2 系统功能设计
[2] 2.1 功能分解概览
[Normal] 本平台在功能层面采用"主题模块化"的方式进行划分。每个一级模块对应党支部日常工作中的一类相对独立的事务主题（学习、自测、写作、会议、发展党员、台账），再加上一类横向的系统管理模块，共构成七个一级模块。模块下进一步分解为可独立交付的二级子功能。
[Normal] 图 2.1 系统功能结构图
[Normal] 
[Normal] 系统功能结构图采用三层树形结构呈现：第一层为系统名称（本平台 系统），第二层为七个一级模块并标注优先级（P0 / P1 / P2），第三层为各模块下的具体子功能。
[2] 2.2 功能模块说明
[Normal] 本平台包含七个一级功能模块：学习模块、自测模块、写作模块、会议模块、发展党员模块、台账模块和系统管理模块。其中学习、自测、写作三个模块为 P0 优先级，是 MVP 阶段必须交付的核心模块；会议、发展党员为 P1 优先级，在暑假冲刺阶段实施；台账为 P2 优先级，视时间情况决定是否纳入本毕设范围；系统管理模块横向支撑所有业务模块。以下逐一说明各模块的功能组成。
[3] 2.2.1 学习模块（P0）
[Normal] 学习模块面向党员日常理论学习场景，提供材料查询、问答、学习记录、任务跟踪等子功能。其中"智能问答"是模块核心，党员可就党的理论、党章党规、时事政策等内容向系统提问，系统返回基于知识库的答案并附原文出处；"材料推荐"根据党员学习历史与支部发布任务推送学习内容；"学习记录"自动记录每位党员的学习行为并归档；"任务下发（书记）"与"任务跟踪（书记）"面向支部书记，支持以支部为单位下发学习任务并查看完成情况。
[3] 2.2.2 自测模块（P0）
[Normal] 自测模块为党员提供自主练习与考核两类场景。"自由练习"按党员自选范围出题、即时讲解；"专项自测"围绕某一主题（如二十大精神、新党章修订内容）集中出题；"错题本"沉淀党员历史答错题目用于反复练习；"考试下发（书记）"由书记针对特定群体下发限时考试，"成绩统计（书记）"汇总参考人员成绩。模块在结构上与学习模块对称——党员侧三块（自由练习、专项自测、错题本）加书记侧两块（考试下发、成绩统计）。
[3] 2.2.3 写作模块（P0）
[Normal] 写作模块为党员提供以 AI 辅助为主的写作支持，覆盖思想汇报、年度总结、民主评议自评、入党申请、心得体会、历史范本管理六类场景。模块设计采用"轻版"实现——只做"用户输入要点 → AI 生成草稿 → 用户保存或导出"的单向辅助，不做"提交 → 书记审阅 → 反馈 → 归档"的工作流。该决策的考虑是：工作流版工程量大且涉及党员档案合规，与本毕设的"Agent 辅助而非替代组织流程"定位不符；轻版在数据库中预留 status 字段，未来可平滑扩展为工作流。
[3] 2.2.4 会议模块（P1）
[Normal] 会议模块面向"三会一课""组织生活会""主题党日""会议纪要"等支部会议场景。其中"会议纪要 AI 辅助"是模块的研究亮点——支部书记上传会议录音或会议要点，系统自动生成结构化纪要初稿（包含会议时间、出席人员、议题、决议、下一步行动等字段），书记审核后归档。该模块在 P1 阶段实施，不进入 MVP 范围。
[3] 2.2.5 发展党员模块（P1）
[Normal] 发展党员模块面向支部书记，覆盖入党申请到正式党员的完整流程节点（申请人管理、入党积极分子管理、发展对象管理、预备党员管理、转正流程、材料归档）。模块的核心价值是把组织部规定的发展党员流程显式化、节点化，辅以模板与提醒，降低新任书记的学习成本。该模块在 P1 阶段实施。
[3] 2.2.6 台账模块（P2）
[Normal] 台账模块为支部书记提供数据归集与导出能力，包括党员名册、党费台账、学习台账、活动台账、统计报表等。台账模块的特点是"数据消费层"——它本身不产生新业务数据，而是把学习、自测、会议等模块沉淀的数据按支部书记的工作习惯重新组织呈现。该模块在 P2 阶段实施，如时间紧张可降级为"业务数据 CSV 导出"。
[3] 2.2.7 系统管理模块
[Normal] 系统管理模块为系统运维与配置提供基础能力，包括党员账号管理、支部组织管理、权限角色管理、积分规则管理、知识库管理。该模块横向支撑所有业务模块，本身不对应单一业务场景，因此在系统功能图中独立成一类。
[2] 2.3 优先级划分依据
[Normal] 七个模块的优先级（P0 / P1 / P2）依据三个维度综合判断：党员日常使用频次、对支部书记的工作价值、毕设算法研究价值。其中前两个维度共同决定模块对真实落地的贡献，第三个维度决定模块对论文产出的贡献。

[样式3] 3 系统体系结构设计
[2] 3.1 体系结构总览
[Normal] 本平台在体系结构层面采用"用户接入—应用编排—算法服务—数据存储"四层主体架构,并将依赖外部资源的大模型推理独立成"外部模型层",构成"四层主体 + 一层外部"的整体形态。这一结构在经典三层架构(表示层 / 业务层 / 数据层)的基础上做了两处针对 AI 系统特点的调整:其一,把 AI 系统中并非普通业务逻辑的"算法逻辑"从应用层中剥离,独立成层,以匹配本平台"应用工程 + 算法能力"双线推进的目标定位;其二,把数据合规边界在架构层面显式化,而不是隐藏在某个组件内部。

[2] 3.2 各层职责详述
[3] 3.2.1 用户接入层
[Normal] 用户接入层提供三个入口：面向党员日常使用的微信公众号（P0，本毕设核心交付），面向支部书记后台管理的 Web 管理后台（P2，延后实现），以及面向教师使用扩展模块的独立 Web 前端（扩展模块专用）。多入口设计的目的是适配不同角色的使用场景——党员在微信中接收任务、提问与学习，符合现有党务工作的微信群习惯，使用门槛最低；书记侧涉及批量管理、台账导出等操作，更适合在 PC 浏览器中完成；教师侧需要上传课件、提纲等教学材料并查看生成的脚本与视频，独立部署避免与党员入口和书记后台的权限模型混淆。三个入口最终汇入同一应用编排层，共享下层全部业务能力。
[3] 3.2.2 应用编排层（Dify）
[Normal] 应用编排层基于开源应用编排平台 Dify 私有部署实现，承担四类职责：对话管理、工作流编排、轻量知识库、路由分发。其中"轻量知识库"用于存放 FAQ、通知公告等平面化内容，直接由 Dify 自带 RAG 处理，不需要复杂的层级解析；需要结构化检索的核心党建文档（如《党章》《网络行为规范》）则不放在 Dify 内部知识库，而是通过"路由分发"节点交给算法服务层的层次化 RAG 服务处理。"直连简单对话"是路由分发的另一条路径——对于不需要专业检索的闲聊或事实型问答，Dify 可直接调用外部模型层，这部分场景不必走自研算法，以节省调用开销。
[3] 3.2.3 算法服务层（自研 / Python FastAPI）
[Normal] 算法服务层是本毕设的核心研究产出所在，采用 Python + FastAPI 独立部署，与 Dify 通过 HTTP API 通信。该层包含三个子服务：层次化 RAG 服务作为主算法，针对党建文件章 / 节 / 条 / 款的强结构特征做多层检索；合规生成服务作为次算法，在生成阶段对涉政表述做约束；跨域对齐服务作为扩展模块的核心算法组件，负责党员理论域与课程教学域之间的语义对齐。三个子服务的具体方法、实验设计与评估指标在本文档中不展开，将在大论文专门的算法章节中独立陈述。
[Normal] 三个子服务的一句话定位如下：
[Normal] a. 层次化 RAG 服务（主算法）。 针对党建文件章 / 节 / 条 / 款的强结构特征，实现"粗粒度章节检索 → 细粒度条款检索 → 检索结果重排"的多层检索流水线，并在每一层附加层级元数据，使生成结果可直接引用条款编号。该服务由五个子模块构成：结构化解析器、层次化切片器、元数据增强器、多层级检索器、检索结果重排器。
[Normal] b. 合规生成服务（次算法）。 在 LLM 生成阶段引入"采样—评分—筛选"机制，以一个轻量级合规性评分器对候选回答打分，选最优；评分器不通过时降级为"检索增强引用"模式，直接返回原文。
[Normal] c. 跨域对齐服务（扩展模块核心组件）。 面向党建文献与专业课程教材的双语料对齐问题，在六项原则约束下实现党员理论域与课程教学域的语义对齐，为扩展模块的脚本生成提供对齐后的融合内容。该服务的完整设计见第 7 章。
[3] 3.2.4 数据层
[Normal] 数据层采用"三库分工"策略：PostgreSQL 存储党员档案、学习记录、积分日志等结构化业务数据，是系统中数据规模最大、写入频率最高的核心库；Qdrant 存储党建文档的向量嵌入及其层级元数据，服务于层次化 RAG 服务，选型理由见 3.3 节；文件存储保留党建文件的原始 PDF / Word，用于检索结果回溯与原文展示。三类数据物理隔离但逻辑关联——PostgreSQL 中的业务记录通过外键引用文档 ID，Qdrant 中的向量切片通过 metadata 关联文档 ID 与层级路径，文件存储中的原文与上述两库通过文档 ID 索引。具体表结构与字段说明见第 6 章数据库设计。
[3] 3.2.5 外部模型层
[Normal] 外部模型层在 Demo 阶段调用 DeepSeek V4 API，包括 Flash 版本（用于轻量任务，如简单问答、文本润色）与 Pro 版本（用于复杂任务，如结构化生成、长文本理解）。该层在体系结构图中以独立分组、虚线边框、异色填充的方式呈现，目的是把数据合规边界在架构层面显式化：跨过这一边界的请求文本必须经过算法服务层中的脱敏中间件预处理，确保党员姓名、身份证号、电话号码等 PII 信息不离开校园网。生产阶段的合规方案（本地化部署或学校已有私有大模型）将在与学校对齐合规要求后再做决策，届时该层将物理上回到校园网内，但分层结构保留——因为"模型推理"与"应用业务"在职责上本就应该解耦。
[2] 3.3 关键设计决策
[3] 3.3.1 为何采用"Dify + 党务 AI 大模型"解耦架构
[Normal] 本系统在选型阶段面临三个核心约束：数据合规（党务数据涉及党员档案，不可使用境外或商业 SaaS 平台）、工期约束（8 个月内同时交付产品和论文）、毕设深度（需要有可独立评估的算法研究产出）。三个约束共同反推出对底座的要求——必须开源可私有部署、必须能快速搭出可用产品、必须不把核心算法封死在框架里。
[Normal] 表 3.1 应用底座候选方案对比
[Normal] 最终方案让 Dify 承担"应用壳子"——做对话编排、知识库管理、多应用切换等成熟工作；而把毕设要做透的层次化检索、合规生成、跨域对齐三个算法独立成 Service，通过 HTTP API 与 Dify 通信。这一架构使得论文核心贡献（算法服务层）在工程上是可独立评估、可单独消融实验、可单独开源的研究产出，同时不影响产品端的快速迭代。
[3] 3.3.2 为何将外部模型层独立成层并标注合规边界
[Normal] 党务数据的合规红线是"数据不出校园"，但 Demo 阶段受 GPU 资源限制无法本地部署 DeepSeek V4（参数规模约 1.6T，本地推理对显存的要求超出当前可获得的资源），只能调用官方 API。这意味着系统中存在一条唯一的跨域数据流——从算法服务层到外部模型层。将该层在体系结构图中独立画出（虚线框 + 异色），目的是让这条数据流在架构层面显式可见，而不是隐藏在某个组件内部：它强制系统在该边界处必须有脱敏中间件、必须有审计日志、必须在合规方案中被单独讨论。
[3] 3.3.3 为何选择 Qdrant 作为向量数据库
[Normal] 向量数据库选型时对比了 Milvus、Weaviate、PGVector、Chroma 与 Qdrant 五个候选。判断维度主要有三：党建文档特征匹配度（长文本、结构化强、需要丰富元数据过滤）、Dify 集成成本、答辩友好度。最终选择 Qdrant 的具体理由是：对元数据过滤的支持完善（便于层次化 RAG 中按章 / 节 / 条做精细化筛选）、单 Docker 容器部署轻量（校园网服务器资源有限可承受）、Rust 实现的性能在数据量增长后仍有空间、Dify 原生支持零集成成本、社区活跃且主流不大材小用。
[3] 3.3.4 Dify 内置知识库与党务 AI 大模型知识库的分工
[Normal] Dify 自带的知识库与党务 AI 大模型的层次化 RAG 在功能上有重叠，如何划分两者的职责需要明确决策。本系统的分工是：Dify 自带知识库放轻量级、平面化的内容，如 FAQ、通知公告、流程手册等无强层级结构的文档；党务 AI 大模型处理需要层次化 RAG 的核心党建文档，如《党章》《网络行为规范》《中国共产党党员教育管理工作条例》等具有强烈章 / 节 / 条 / 款结构的文件。两者共用同一 Qdrant 实例但使用不同 collection，在物理资源上不重复建设、在业务逻辑上职责分离。
[3] 3.3.5 为扩展模块预留集成接口
[Normal] 通识模块与扩展模块在体系结构上共享算法服务层的基础能力。具体而言：Dify 实例可通过多应用机制添加扩展模块的应用入口；党务 AI 大模型中的层次化 RAG、合规生成等能力可被扩展模块复用，跨域对齐服务本身就是扩展模块的核心组件；数据层通过 schema 隔离实现通识模块与扩展模块数据互不干扰。扩展模块的教师入口采用独立 Web 前端部署，不复用党员公众号或书记 Web 后台，以保持角色与权限的清晰分离。

[3] 4.2.1 校园网外（公网）
[Normal] 公网区域包含三类参与方：党员手机（党员用户的微信应用所在终端）、微信服务器（腾讯机房，作为消息中转与公众号能力提供方）、支部书记电脑（书记在校外远程工作时的终端，通过校园 VPN 接入）。这一区域中的设备并非系统的内部组件，但因为系统必须通过它们与最终用户交互，所以在拓扑图中作为外部环境完整呈现，以体现系统真实的物理通信链路。
[3] 4.2.2 校园网边界（DMZ / 防火墙）
[Normal] 校园网边界由学校防火墙与反向代理 Nginx 构成，承担两类职责：其一，作为公网到校园网的唯一入口，完成 HTTPS 终止与端口转发，把外部流量转发到内网应用服务器；其二，作为校园 VPN 的接入点，允许书记在校外通过 VPN 拨入后访问内网管理后台。Nginx 不仅是流量代理，也是加密边界——所有跨边界流量在此处完成 HTTPS 终止，内网内部使用 HTTP 通信以降低性能开销。
[3] 4.2.3 校园网内（私有部署区，数据合规边界）
[Normal] 校园网内是系统主体所在区域，内部进一步分为两个子区：应用服务器（逻辑分离的 Docker Compose 单机部署）与数据存储。应用服务器子区运行三个核心容器——Dify 容器（端口 5001，承担应用编排）、算法服务容器（基于 FastAPI，端口 8000，内含脱敏中间件，承担层次化 RAG / 合规生成 / 跨域对齐三个子服务）、以及教师 Web 前端容器（扩展模块专用，端口待定）；数据存储子区运行 PostgreSQL（端口 5432，存党员档案与业务数据）、Qdrant（端口 6333，存向量与元数据）、文件存储（存党建原始文档）三类持久化组件。这一区域的网络出口受学校防火墙严格管控，默认禁止主动出站，只对算法服务容器到 DeepSeek API 的特定 HTTPS 出站连接开放白名单。
[Normal] 需要明确强调的是，"校园网内"的边界即是数据合规边界。所有党员的原始 PII 数据（姓名、身份证号、电话、微信 OpenID 等）只在该区域内流转；唯一的跨域数据流是从算法服务容器到 DeepSeek API 的请求文本，该数据流在跨过边界前必须经过算法服务容器内的脱敏中间件处理。

[样式3] 5 系统数据流设计
[2] 5.1 数据流图分层方法
[Normal] 数据流图（Data Flow Diagram, DFD）是软件设计中用来描述系统中数据如何被产生、加工、存储和消费的可视化建模方法。它由四类基本元素构成：外部实体（矩形，代表系统边界以外与系统交互的人或外部系统）、加工（圆形或圆角矩形，代表系统内部的处理过程）、数据存储（开口矩形或双横线，代表数据的持久化容器）、以及连接它们的数据流箭头（代表带有数据内容的有向流动）。
[Normal] 本系统采用分层 DFD 的方法呈现：0 层（顶层 / 上下文图）把整个系统抽象为单一加工，只刻画系统与外部实体之间的输入输出关系，目的是在最高层面回答"这个系统跟外界交换什么数据"；1 层把 0 层中那个单一加工分解为系统内部的若干子加工，把数据存储显式画出，目的是回答"数据在系统内部如何流转、被谁加工、存到哪里"。本设计文档画到 1 层为止，不再向下分解到 2 层——理由是 1 层已经足以支撑后续软件实施阶段的接口与模块划分。
[2] 5.2 顶层数据流图（0 层）
[Normal] 0 层数据流图把整个本平台 系统抽象为单一加工节点，描述其与外部环境的全部数据交换。系统识别出四类外部实体：党员、支部书记、微信平台、DeepSeek API。前两类是系统的最终使用者（实线表示），后两类是系统在运行时必须依赖但不属于系统主体的外部系统（虚线表示，与跨边界数据流共同呈现合规属性）。

[3] 5.4.1 把智能问答（P4）单独作为一个加工
[Normal] 从纯业务视角看，智能问答可以视为"学习管理"的子功能。但本设计选择把 P4 与 P1 平级、单独成为一个加工，理由是：智能问答承载的是本毕设的核心研究产出——层次化 RAG 算法。把它独立成加工，使其在数据流图中具有与其他业务加工相同的可见度，便于在后续详细设计与论文撰写中作为独立的研究单元处理。
[3] 5.4.2 跨边界数据流的显式标注
[Normal] 1 层数据流图中，P3 写作辅助与 P4 智能问答到 E4 DeepSeek API 的两条数据流采用红色虚线特殊标注，并附文字说明"脱敏后的提问 + 上下文""脱敏后的写作要点"。这一标注的目的是把合规边界从体系结构图、部署拓扑图延续到数据流图——三张图共同呈现同一条边界，使"数据是否出校园"在三个不同视角下都有明确答案。
[3] 5.4.3 积分计算（P5）采用事件驱动而非请求驱动
[Normal] P5 与其他四个加工的衔接关系不同：P1、P2、P3、P4 均由用户请求直接驱动（党员或书记发起），而 P5 由其他加工产生的"积分事件"驱动，本身不直接接收用户请求。在数据流图上表现为：P1 / P2 / P3 向 P5 发出积分事件流（完成学习 / 答对 / 写作完成），P5 接收事件后写入 D5 积分日志库。这一设计使积分逻辑与业务逻辑解耦——业务模块只负责发出"我做了什么"的事件，不需要关心积分规则；P5 单独负责把事件按规则转化为积分。该设计与积分采用事件溯源模式的决策一致。

[样式3] 6 数据库概念设计与数据字典
[2] 6.1 数据库概念设计概述
[3] 6.1.1 设计原则与命名约定
[Normal] 数据库设计是软件设计文档中颗粒度最细、对后续编码影响最直接的章节。本系统的数据库设计遵循以下五条原则。
[Normal] a. 面向业务实体建模，而非面向页面或接口建模。 数据库结构反映的是党务工作中的真实业务实体（党员、支部、学习材料、任务、答题记录等）及其关系，而不是某个具体页面或 API 的数据组装结构。这一原则保证数据库结构在前端页面或接口形态变化时仍然稳定。
[Normal] b. 命名约定统一为 snake_case。 所有字段名采用小写字母 + 下划线分隔的形式（如 birth_date、branch_id、created_at），实体名（表名）采用 PascalCase（如 Member、LearningMaterial、PointRecord）。这一约定与 PostgreSQL 的主流 ORM（如 SQLAlchemy）的默认行为兼容。
[Normal] c. 主键统一为自增 BIGINT。 所有业务表使用代理主键 id（BIGINT），不使用业务字段作为主键（如不使用身份证号作为党员表主键）。理由是业务字段可能因为合规要求需要修改、加密或替换，使用代理主键可以隔离这种变化。
[Normal] d. 时间字段统一使用 TIMESTAMP，日期字段使用 DATE。 需要精确到秒的时间戳（创建时间、更新时间、答题时间等）使用 TIMESTAMP；只表示日期的字段（出生日期、入党日期、发布日期等）使用 DATE。所有 _at 后缀字段均为 TIMESTAMP。
[Normal] e. 多对多关系一律通过关联表实现，不使用 PostgreSQL 的数组类型或 JSON 字段存关系。 本系统中存在四组多对多关系——任务与材料、任务与党员、考试与题目、考试与党员——分别通过 TaskMaterial、TaskAssignment、ExamQuestion、ExamAssignment 四张关联表实现。

[3] 6.3.5 积分类（1 张）
[Normal] PointRecord（积分记录表）。 本系统数据建模上最值得讲清楚的一张表。该表采用事件溯源（Event Sourcing）模式实现——每次党员的积分变动产生一条新记录，而不是在 Member 表上累加 total_points 字段。Member 的当前总积分由 SELECT SUM(points) FROM PointRecord WHERE member_id = ? 算出。该设计带来三方面收益：（1）可追溯——党员问"我这 50 分怎么来的"可以列出每一笔的来源；（2）可撤销——发现积分错误时通过追加冲账记录纠正，不破坏历史；（3）可分析——按 action / source_type 字段分组统计，可回答"学习类活动贡献了多少分"等运营问题。
[Normal] source_id 与 source_type 两个字段实现"多态外键"——指向产生这条积分的源记录。source_type 取值为产生该积分事件的实体名（如 LearningRecord / TaskAssignment / AnswerRecord / WritingRecord / ExamAssignment / Manual），source_id 是该实体表中对应记录的主键。

[2] 7.1 扩展模块定位与目标
[Normal] 课程课程思政短视频脚本生成系统是本平台的扩展模块,服务于"党员理论学习与教师专业课融合"场景。本平台的核心算法即党务 AI 大模型,在算法服务层面由层次化检索、合规生成、跨域对齐三个子组件协同实现;扩展模块在此基础上做专项延伸,聚焦"党员理论域 ↔ 课程教学域"的跨域融合问题。
[Normal] 本扩展模块的核心目标是:坚持把本学年共产党员应知应会理论学习,与教师日常教学、课堂育人、师德师风、教研教改等实际工作深度融合、一体推进,杜绝理论学习与教学工作"两张皮",做到以理论铸魂、以学习赋能、以实干践行初心使命。
[Normal] 本扩展模块在本毕设中独立成章,章节内重心放在算法设计,具体算法在 7.4 节展开。
[2] 7.2 六项原则约束体系
[Normal] 扩展模块的脚本生成过程受课程思政教学案例内容选取的六项原则约束。这六项原则来自吴老师提供的教学规范文件，作为系统的核心约束规则（等价于"第一准则"），在算法层面建模为生成约束条件。
[Normal] a. 与学科专业相关性原则。 结合课程所归属和服务的学科与专业的形成背景、发展历程、现状和未来趋势，特别是所涉及的重大工程和科学技术发展成果，挖掘其中所蕴含的使命感、责任感、爱国精神、奋斗精神、开拓精神等思政元素。
[Normal] b. 符合职业发展要求原则。 结合不同专业的人才培养特点以及学生未来所从事工作的职业要求，从职业素养养成的角度，有针对性地挖掘课程所蕴含的育人元素，增强育人的针对性和实效性，提升学生职业发展能力。
[Normal] c. 结合热点时事对比原则。 从国际国内两个大局热点时事资源背景中挖掘课程所蕴含的思政元素，教会学生用正确的立场观点方法认识并分析问题，让学生深刻认识世界、理解中国、增强民族自信心和社会责任感。
[Normal] d. 历史与现实分析原则。 从大师的成长道路到校友的成功经验，到教师个人经历中的值得借鉴的经历，甚至社会上一些失败教训和警示性问题。讲好历史与现实的故事，引导学生从中发掘价值观、形成正确的判断事物标准和价值追求。
[Normal] e. 注重家国情怀培养原则。 根据教学需要，选取改革发展稳定、内政外交国防、治党治国治军各方面取得的巨大成就，以及中国特色社会主义在本地区的实践成果进行案例撰写，积极传播和弘扬中华优秀传统文化、革命文化和社会主义先进文化。
[Normal] f. 注重实践体验挖掘原则。 选取学生在实践过程中能够通过身体力行深刻感悟的思政元素，使之内化为学生的精神追求、外化为学生的自觉行动。思政元素包括制度敬畏与自觉遵守、环境保护、珍惜生命、客观严谨细致的科学精神、团队协作、发现与质疑、探索精神、创新思维等。

[3] 8.2.1 积分系统采用事件溯源模式
[Normal] 积分系统的数据模型在设计阶段有两条候选路径。路径一是在 Member 表中增加 total_points 字段，每次发生积分变动时直接对该字段做加减；路径二是建立独立的 PointRecord 日志型表，每次积分变动都新增一条记录，Member 的总积分由 PointRecord 表 SUM 算出。
[Normal] 本系统选择路径二（事件溯源模式）。核心理由是：路径一只保留"现在的积分是多少"这一状态，而路径二同时保留"每一次积分如何变化"的完整历史。对一个党务系统而言，后者带来三方面的具体价值：可追溯（党员问"我这 50 分是怎么来的"可以列出每一笔的来源）、可撤销（发现积分规则错了可以通过追加冲账记录纠正）、可分析（按 action 字段统计各类活动的积分贡献）。从工程实施角度，事件溯源模式带来的额外开销是查询时需要 SUM（可加索引控制成本），对学院级别的数据规模可以忽略。
[3] 8.2.2 写作模块只做 AI 辅助轻版，不做工作流
[Normal] 写作模块在 V1 设想中有完整组织流程版本。在 V2 阶段经过明确决策，确定本毕设范围内只做轻版。这一决策有三层考虑：第一层是合规层面——工作流版会涉及把党员的思想汇报等敏感文本在系统中流转，需要与学院党委对齐才能设计稳妥；第二层是定位层面——本系统是"Agent"，核心价值是辅助而不是替代组织流程；第三层是工程层面——轻版可在 P0 阶段交付。数据库层面的兼容性已在设计中预留：WritingRecord 表中 status 字段保留为 VARCHAR(32)，未来可平滑增加状态值。
[3] 8.2.3 E-R 实体命名采用英文，论文中用实体说明表对照
[Normal] E-R 图与数据字典中的实体名称统一使用英文（Member、Branch、LearningMaterial 等），不进行中文化命名。英文命名的好处包括：与 SQL 语法、ORM 框架、代码变量自然兼容；符合主流数据库设计教材与企业实践规范。中文论文阅读体验的问题通过"实体说明表"解决：在数据字典章节中，每张表都附一段中文实体说明。
[3] 8.2.4 层次化 RAG 拆为五个子模块的设计
[Normal] 层次化 RAG 是本毕设的主算法。在算法服务的内部设计上，将其拆为五个子模块：结构化解析器、层次化切片器、元数据增强器、多层级检索器、检索结果重排器。这一拆分不是任意的——五个子模块对应层次化 RAG 中五个可独立替换、可独立评估的处理阶段。从工程上，每个子模块可以独立单元测试，也可以独立替换实现。从研究上，五个子模块为消融实验提供了天然的对照组——论文中可以设计"去掉元数据增强器""去掉重排器""把多层级检索器换成单层平面检索器"等多种消融配置，定量评估每个子模块对整体性能的贡献。
[Normal] 
[样式3] 9 实施约束与待确认项
[Normal] 本章列出当前软件设计中，部分依赖于学院或学校层面进一步对齐才能最终确定的事项。这些事项不影响整体设计的成立，但其最终形态需要在与相关方对齐后做对应的局部调整。
[2] 9.1 公众号主体归属
[Normal] 系统以微信公众号（服务号）作为面向党员的日常入口，这要求公众号必须挂靠具有事业单位 / 学校主体资质的实体。当前可选方案有两种：挂载到学院已有公众号，作为新增的菜单与功能模块接入；或者以教师第一支部名义申请独立的服务号，经学院党委审批后启用。两种方案在权限、运营、备案流程上有显著差异，需要在与学院党委沟通后再做决定。本设计文档中相关的接口设计在两种方案下均可适用，只是部署阶段的具体值需要替换。
[2] 9.2 校园网内部署资源
[Normal] 系统在校园网内的部署需要一台具备充足资源的服务器作为应用与数据存储宿主机。当前对硬件资源的最低预估为：4 核 CPU、16 GB 内存、500 GB 存储，无 GPU（因为大模型推理走外部 API，本地不承担推理）。如未来切换到本地化部署模型，则需要额外协调至少一张 24 GB 显存的 GPU。具体的服务器获取路径需要在与学院或信息中心沟通后确定。
[2] 9.3 合规边界的最终形态
[Normal] 当前设计中，跨合规边界的数据流是"算法服务容器 → DeepSeek API"，前提是 Demo 阶段允许把脱敏后的请求文本送往境内但非校园内的服务。生产阶段的合规要求可能更严格。本设计文档对体系结构的分层（把外部模型层独立成层）使得这一切换在工程上是可行的：无论是切换到本地部署的开源模型（如 Qwen 32B 等），还是切换到学校已有的私有大模型服务，只需要替换外部模型层的具体实现，算法服务层与上层应用不受影响。
[2] 9.4 数据集与测试集来源
[Normal] 系统中三类数据需要在实施阶段持续补充：其一是党建文档库的内容，需要陆续录入《党章》《网络行为规范》《党员教育管理工作条例》以及学院相关党建文件；其二是评估算法效果的测试集，层次化 RAG 与合规生成两个算法都需要标注好的"问题—答案—相关条款"三元组数据，目前规划的来源是基于 12371 共产党员网党务问答板块的真实党员问题做整理，辅以人工标注与 LLM 辅助生成；其三是党员真实使用数据，这部分数据在系统试点上线后由实际使用产生。
[Normal] 
[样式3] 10 结论
[Normal] 本设计文档对"基于 Dify 的高校 AI 党务平台"进行了完整的软件设计,覆盖系统功能设计、体系结构设计、部署拓扑、数据流设计、数据库概念设计与数据字典、以及扩展模块的算法设计六个方面。
[Normal] 在通识模块方面,本平台采用"Dify 应用编排 + 党务 AI 大模型"的分层架构,以微信公众号为党员入口,覆盖学习、自测、写作、会议、发展党员、台账、系统管理七个功能模块,数据库设计包含 15 张表的完整数据字典。在数据合规方面,本平台以"数据不出校园"为最高约束,在体系结构图、部署拓扑图、数据流图三个视角下对合规边界做了一致性标注。
[Normal] 在扩展模块方面,本平台设计了课程思政短视频脚本生成系统,以六项原则为约束,通过跨域语义对齐将党员理论与教师专业课内容融合,生成结构化故事脚本并导入第三方视频引擎产出教学短视频。该模块在设计层面完整呈现,在实施层面精简验证。后续工作将按 P0 → P1 → P2 的优先级顺序推进系统实施。
