## 摘要

本设计文档是"基于 Dify 的高校党务 AI 平台设计开发"毕业设计项目的软件设计文档，对系统的功能划分、整体架构、部署形态、数据流向、数据库结构以及扩展模块的算法设计进行完整描述，作为后续软件实施阶段的设计依据。系统面向高校各级党支部的日常党务工作场景，以微信公众号作为党员日常入口，以开源应用编排平台 Dify 作为应用层底座，以党务 AI 大模型作为核心检索与生成引擎，覆盖学习、自测、写作、会议、发展党员、台账、系统管理七个通识功能模块。在通识模块之外，系统设计了面向"党员理论学习与教师专业课融合"场景的扩展模块——课程思政短视频脚本生成系统，该模块将党员应知应会的理论内容与教师的专业课教学内容相结合，在课程思政教学的六项原则约束下，生成可用于驱动视频生成引擎的脚本，产出教学短视频。系统在技术架构上采用"应用编排层与算法服务层解耦"的设计，使算法研究产出可独立评估、可单独迭代、可独立开源；在数据合规上以"数据不出校园"为最高约束，跨合规边界的数据流在架构层面显式标注并经脱敏处理。本文档覆盖系统的完整设计，通识模块的 P0 部分将在 5–6 月实施，扩展模块在设计阶段完整呈现、实施阶段精简验证。

**关键词**：党务管理；智能 Agent；检索增强生成；Dify；课程思政

## Abstract

This document presents the software design for the graduation project "Design and Development of a University Party Affairs AI Platform Based on Dify." The system serves daily party affairs scenarios in university-level party branches, using a WeChat Official Account as the primary user interface, the open-source Dify platform as the application orchestration layer, and a self-developed algorithm service as the core retrieval and generation engine. It covers seven general-purpose modules including study, self-assessment, writing assistance, meetings, party member development, ledger management, and system administration. An extension module — a curriculum-based ideological education short video script generation system — is designed to align party theory with professional course content under six pedagogical principles, producing structured storyboard scripts for video generation. The system architecture decouples the application layer from the algorithm service layer, enabling independent evaluation and ablation experiments. Data compliance follows a strict "data stays on campus" policy with explicit boundary annotations across all design views.

**Key Words**: party affairs management; intelligent agent; retrieval-augmented generation; Dify; curriculum-based ideological education

## 1 绪论

### 1.1 文档目的与范围

本文档是"基于 Dify 的高校 AI 党务平台设计开发"毕业设计项目的软件设计文档（V4），按照《西安工业大学毕业设计管理手册》撰写规范重新组织，对系统的功能划分、整体架构、部署形态、数据流向、数据库结构以及扩展模块的算法设计进行完整描述，作为后续软件实施阶段的设计依据。本文档的覆盖范围包含本平台的完整设计：面向党员日常使用的通识模块（学习、自测、写作、会议、发展党员、台账、系统管理）和面向"党员理论学习与教师专业课融合"场景的扩展模块（课程思政短视频脚本生成系统）。通识模块的 P0 部分将在 5–6 月实施，扩展模块的设计在本文档中完整呈现，实施阶段精简验证。

### 1.2 系统定位

基于 Dify 的高校 AI 党务平台是一个面向高校各级党支部的 AI 党务工作助手。系统以微信公众号（服务号）作为面向党员的日常入口，以 Dify 作为开发平台，以党务 AI 大模型作为核心检索与生成引擎，服务于支部书记、支部委员与普通党员的日常党务工作，核心覆盖学习、自测、写作三类高频场景，并在 P1、P2 阶段逐步扩展会议、发展党员、台账等场景。

本系统立足于实际应用，以 AI 大模型与自动化技术为核心驱动，实现党务管理、党员教育、组织建设的智能化升级。系统采用私有化部署 + 党建专属知识库 + 智能应用模块的常见形态，依托党建专属大模型实现智能文稿生成、政策智能问答、内容合规风控、党建数据分析；结合流程自动化能力完成党务流程流转、台账报表自动生成、会议全流程闭环、任务智能督办，全面实现党务工作智能化、标准化、轻量化。通过知识管理，实现党务工作与具体业务结合的创新，将时政理论与教师日常教学、课堂育人、师德师风、教研教改等实际工作深度融合、一体推进，做到以理论铸魂、以学习赋能、以实干践行初心使命。扩展模块的算法将在第 7 章独立展开。

### 1.3 设计原则

**a. 数据合规优先。** 党务数据涉及党员档案、组织内部资料，党内活动属于"私密文件"范畴。系统在选型与部署的所有环节，均以"数据不出校园"为最高约束。所有可控组件部署在校园网内私有环境；无法在本地承载的大模型推理被独立成"外部模型层"，跨边界的数据流统一经过脱敏中间件处理。

**b. 应用与算法分层。** Dify 承担应用层职责（对话编排、知识库管理、工作流配置）；党务 AI 大模型在算法服务层提供核心检索与生成能力，两者通过 HTTP API 通信。这一分层使得算法能力可独立迭代，同时不影响产品端的快速交付。

**c. 面向多角色与多入口。** 系统同时服务党员（高频、日常使用）、支部书记（中频、管理使用）与教师（扩展模块使用）三类角色，因此在用户接入层划分了微信公众号（P0，党员）、Web 管理后台（P2，书记）与独立 Web 前端（扩展模块，教师）三个入口，而非把所有功能挤进单一终端。

**d. 为扩展模块预留接口。** 通识模块与扩展模块在体系结构上共享算法服务层的基础能力，扩展模块在此基础上做研究方向的延伸，具体算法在第 7 章展开。设计上保证通识模块的部署形态可承载扩展模块的接入，不需要重构底层架构。

## 2 系统功能设计

### 2.1 功能分解概览

本平台在功能层面采用"主题模块化"的方式进行划分。每个一级模块对应党支部日常工作中的一类相对独立的事务主题（学习、自测、写作、会议、发展党员、台账），再加上一类横向的系统管理模块，共构成七个一级模块。模块下进一步分解为可独立交付的二级子功能。

**图 2.1 系统功能结构图**

系统功能结构图采用三层树形结构呈现：第一层为系统名称（本平台系统），第二层为七个一级模块并标注优先级（P0 / P1 / P2），第三层为各模块下的具体子功能。

基于 Dify 的高校 AI 党务平台是一套面向党建工作全流程的智能化管理平台，通过模块化设计，将党务工作拆解为多个功能模块，实现党建工作的标准化、流程化、高效化管理，核心模块及功能如下。

模块优先级划分，系统模块按开发优先级分为三类：

- **P0 模块（基础核心）**：学习模块、自测模块、写作模块，为党建学习与基础材料处理提供支撑；
- **P1 模块（流程核心）**：会议模块、发展党员模块，覆盖党建核心业务流程；
- **P2 模块（管理支撑）**：台账模块、系统管理模块，提供数据管理与系统运维保障。

### 2.2 各模块功能详解

#### 2.2.1 学习模块（P0）

打造一站式党员学习服务，打通学习资源供给与任务管理的全流程闭环，让党员学习更高效、管理更省心。智能答疑，党建知识随问随答，为党员提供即时学习支持。精准学习资源服务，智能匹配并推送学习材料，同时支持关键词检索，快速获取所需内容。学习过程可视化管理，自动记录学习轨迹与进度，学习情况一目了然。书记端任务管理，支持学习任务一键下发、线上签收与进度实时反馈，高效推进学习工作。

#### 2.2.2 自测模块（P0）

为党员学习效果提供一站式检验方案，用科学的测试与数据管理，让学习成果看得见、有反馈。自主练习场景，党员可随时随地开展党建知识练习，灵活巩固所学内容。专项主题测试，针对重点政策、主题开展专项自测，强化核心知识掌握。错题智能管理，自动归集错题，打造专属错题本，支持反复练习、精准补弱。书记端考试管理，一键发起线上考试，自动完成成绩统计与报表生成，大幅降低组织管理成本。

#### 2.2.3 写作模块（P0）

AI 赋能党建材料全场景撰写，告别"下笔难、不规范、效率低"的痛点，让党建材料撰写更省心、更专业。思想汇报智能辅助，提供专业框架、优质素材与修改建议，帮助党员快速完成符合规范的思想汇报。年度总结高效生成，一键生成适配不同场景的年度总结模板，搭配针对性优化建议，轻松提升材料质量。民主评议内容支持，提供民主评议材料撰写指引，帮助党员理清思路、规范表达。入党申请规范校验，提供撰写指导与合规性校验，避免格式、内容不规范问题。心得体会思路引导，提供写作框架与参考示例，帮助党员快速提炼观点、写出真情实感。范本库智能调用，沉淀各类党建材料的优质范本，随时可查、可复用，告别重复造轮子。

#### 2.2.4 会议模块（P1）

一站式解决党建会议管理痛点，让会议组织更省心、流程更规范、记录更完整。三会一课线上留痕，告别纸质记录，线上完成会议内容全记录，随时可查、永不丢失。组织生活会闭环管理，从流程管控到材料归档，全程线上化管理，确保环节不遗漏。主题党日活动全链路支持，从计划制定、活动执行到结果记录，全流程数字化管理。智能会议通知，一键推送通知，支持线上回执，轻松掌握参会情况。AI 纪要自动生成，基于会议内容自动生成规范纪要，省去人工整理的繁琐工作。

#### 2.2.5 发展党员模块（P1）

全覆盖党员发展全生命周期流程，实现发展党员工作标准化、流程化、线上化管控。入党申请人管理，统一归集、管理入党申请人基础信息及相关资料。入党积极分子管理，全程跟踪积极分子培养教育、日常考察全流程。发展对象管理，规范完成发展对象资格审查、公示报备等关键环节。预备党员管理，统筹预备党员日常教育、跟踪考察及日常动态管理。转正流程审批，线上闭环办理预备党员转正全流程审批业务。全环节材料归档，自动归集整理党员发展各阶段资料，一键规范归档留存。

#### 2.2.6 台账模块（P2）

实现党建工作数据规范化、体系化台账管理，支撑业务溯源、数据统计与分析研判。党员花名册，统一维护党员基础信息，建立标准化电子名册，实现人员信息集中管控。党员台账，完整记录党员组织关系、学习情况、奖惩荣誉等关键动态信息。学习台账，汇总统计党员学习任务完成进度及各类学习行为数据。活动台账，全面登记党组织开展的各类主题活动、组织活动相关信息。统计报表，自动生成党建工作各类统计报表，支持灵活查询与数据导出。

#### 2.2.7 系统管理模块（P2）

保障平台安全平稳运行，统筹实现账号权限、基础配置及资源库的一体化管控。账号管理，统一负责系统用户账号的新增、编辑、变更与注销全生命周期管理。角色权限管理，依托角色架构进行操作权限批量分配，实现职责与权限精准匹配。分级权限管控，精细化拆解功能权限，按层级、岗位进行授权配置，实现分级分域管控。积分规则管理，自定义配置党员学习、活动参与等行为的积分评定规则与核算标准。知识库管理，统一维护系统内置党建知识库、素材资源库，支持内容更新、分类管理与随时调用。

基于 Dify 的高校 AI 党务平台通过"学习 + 业务 + 管理"一体化设计，解决了传统党务工作中流程繁琐、记录不规范、效率低下的问题，同时借助 AI 辅助能力，大幅降低党建材料撰写、会议管理等工作的人力成本，助力基层党组织实现党建工作的智能化升级。

## 3 系统体系结构设计

### 3.1 体系结构总览

系统体系结构是决定平台可扩展性、可维护性与合规保障能力的基础骨架。本平台在体系结构层面构建了"用户接入—应用编排—算法服务—数据存储"四层主体架构，并将依赖外部资源的大模型推理独立为"外部模型层"，形成"四层主体 + 一层外部"的整体格局。这一架构设计不是对经典三层架构的简单套用，而是针对 AI 驱动型党务系统做了两处关键调整。

其一，将算法逻辑从应用层中剥离、独立成层。在传统业务系统中，业务逻辑层承担全部处理职责即可满足需求；但在 AI 系统中，算法能力（检索、生成、对齐）与业务编排（对话管理、工作流、路由）在研发节奏、评估标准、迭代周期上有着本质差异——前者需要消融实验、指标对比、论文产出，后者需要快速响应业务需求、持续交付。将两者分层，使"应用工程"与"算法研究"两条线可以并行推进、互不阻塞。

其二，将数据合规边界在架构层面显式化。党务系统的合规红线是"数据不出校园"，但 AI 系统天然需要调用外部模型能力。与其让这条跨边界数据流隐藏在某个组件的内部实现中，不如在架构图上将其独立呈现——让合规风险可见、可控、可审计。

### 3.2 各层职责详述

#### 3.2.1 用户接入层

用户接入层为三类角色打造专属入口，实现"角色匹配终端、场景决定形态"的接入体验。面向党员日常使用，以微信公众号作为 P0 核心入口——党员在微信中接收学习任务、提交问题、完成自测，符合现有党务工作的微信群使用习惯，真正做到零学习成本上手。面向支部书记后台管理，以 Web 管理后台作为 P2 入口——书记侧涉及批量任务下发、台账数据导出、党员信息维护等操作密集型工作，PC 浏览器的大屏操作体验远优于手机端。面向教师使用扩展模块，以独立 Web 前端作为专用入口——教师需要上传课件、教学提纲等材料并查看生成的脚本与视频，独立部署确保了与党员入口、书记后台之间权限模型的清晰隔离。三个入口最终汇入同一应用编排层，共享下层全部业务能力，实现"入口多元、能力统一"。

#### 3.2.2 应用编排层（Dify）

应用编排层是平台的"智能调度中枢"，基于开源应用编排平台 Dify 私有部署构建，承担对话管理、工作流编排、轻量知识库与路由分发四大核心职责。Dify 在其中的角色不是"大而全的 AI 中台"，而是专注做好应用层编排——把成熟的对话管理、工作流引擎、知识库管理能力拿过来直接用，把需要深度研究的检索与生成能力通过路由分发交给下层的自研算法服务。

在知识库层面，本层贯彻"轻重分离"策略。轻量级、平面化内容（FAQ、通知公告、流程手册等无强层级结构的文档）直接放入 Dify 自带知识库，由 Dify 内置 RAG 引擎快速处理，保障低延迟、高可用的基础问答体验。需要结构化检索的核心党建文档（如《党章》《网络行为规范》《中国共产党党员教育管理工作条例》等具有强烈章/节/条/款结构的文件）则通过路由分发节点，精准转发至算法服务层的层次化 RAG 服务处理，充分发挥自研算法对党建文件结构特征的深度适配能力。

路由分发还承担一条"直连快速通道"：对于不需要专业检索的闲聊或事实型简单问答，Dify 可直接调用外部模型层完成响应，不必走自研算法的完整检索流水线，在保证回答质量的前提下最大化节省调用开销与响应延迟。

#### 3.2.3 算法服务层（自研 / Python FastAPI）

算法服务层是本毕设的核心研究阵地，也是平台"智能化"能力的技术底座。该层采用 Python + FastAPI 技术栈独立部署，与上层 Dify 通过标准化 HTTP API 松耦合通信，确保算法能力可独立开发、独立测试、独立评估、独立开源。

该层构建了三项协同工作的子服务，每一项都瞄准党务场景中的真实技术挑战：

**a. 层次化 RAG 服务（主算法）。** 党建文件具有天然的章/节/条/款层级结构，传统平面检索将整份文档切成等长片段后丢失了这一结构信息——导致检索结果可能出现"找到了相关段落但不知道它属于哪一章哪一条"的尴尬。层次化 RAG 正是对这一痛点的精准回应：它构建了"粗粒度章节检索 → 细粒度条款检索 → 检索结果重排"的多层检索流水线，在每一层附加层级元数据，使生成结果可以直接引用到具体的条款编号。该服务由五个可独立演进、可独立评估的子模块构成：结构化解析器、层次化切片器、元数据增强器、多层级检索器、检索结果重排器。

**b. 合规生成服务（次算法）。** 党务场景对生成内容的合规性有极高要求——涉政表述一旦失准，后果不是用户体验问题而是政治问题。合规生成服务在 LLM 生成阶段引入"采样—评分—筛选"三级质量把控机制：先生成多个候选回答，再由轻量级合规性评分器对每个候选打分并选最优；当所有候选的合规评分均不达标时，自动降级为"检索增强引用"模式，直接返回带原文出处的检索结果而不做生成。这一机制在"智能生成"与"安全可控"之间找到了工程上可落地的平衡点。

**c. 跨域对齐服务（扩展模块核心组件）。** 面向党建文献与专业课程教材的双语料对齐问题，在六项原则约束下实现"党员理论域"与"课程教学域"之间的语义对齐，为扩展模块的脚本生成提供融合后的高质量内容。该服务的完整设计见第 7 章。

三个子服务的具体方法、实验设计与评估指标将在毕业论文专门的算法章节中独立陈述，本文档聚焦于系统设计层面。

#### 3.2.4 数据层

数据层采用"三库分工、逻辑关联"的存储架构，为平台提供稳定可靠的数据底座。PostgreSQL 承担结构化业务数据的存储职责——党员档案、学习记录、积分日志、任务状态等写入频率最高、一致性要求最强的核心数据全部由它管理。Qdrant 向量数据库承担党建文档向量嵌入及其层级元数据的存储与检索职责，作为层次化 RAG 服务的检索引擎，选型理由在 3.3.3 节详细展开。文件存储保留党建文件的原始 PDF/Word 版本，服务于检索结果回溯与原文展示——当系统返回"根据《党章》第 X 章第 Y 条"时，用户可以一键查看原始文件对应页面，增强答案的可信度与可核查性。

三类数据在物理上隔离部署、独立运维，在逻辑上通过统一的文档 ID 实现关联——PostgreSQL 中的业务记录通过外键引用文档 ID，Qdrant 中的向量切片通过 metadata 关联文档 ID 与层级路径，文件存储中的原文通过文档 ID 索引定位。具体表结构与字段说明见第 6 章数据库设计。

#### 3.2.5 外部模型层

外部模型层在当前 Demo 阶段调用 DeepSeek V4 API，按任务复杂度分两档使用：Flash 版本处理轻量任务（简单问答、文本润色），Pro 版本处理复杂任务（结构化生成、长文本理解）。该层在体系结构图中以独立分组、虚线边框、异色填充的方式鲜明呈现——这一视觉处理不是装饰，而是强制传达一条硬性约束：跨过这一边界的所有请求文本，必须经由算法服务层中的脱敏中间件预先处理，确保党员姓名、身份证号、电话号码等 PII 信息绝不离开校园网。

生产阶段的合规方案（本地化部署开源模型如 Qwen 32B，或接入学校已有的私有大模型服务）将在与学校对齐合规要求后决策。届时外部模型层将物理上回归校园网内，但其分层结构保留——因为"模型推理"与"应用业务"在职责上天然就该解耦，这一分层不会因部署位置的变化而失去意义。

### 3.3 关键设计决策

#### 3.3.1 为何采用"Dify + 党务 AI 大模型"解耦架构

本系统在技术选型阶段面临三个相互制约的核心约束。数据合规：党务数据涉及党员档案，任何商业 SaaS 平台或境外服务均不可使用。工期约束：8 个月内需要同时交付可运行的产品和达到答辩要求的论文。深度约束：毕设必须有可独立评估、可消融实验的算法研究产出，不能止步于"调了个 API"。

三个约束共同反推出对技术底座的硬性要求——必须开源可私有部署（应对合规）、必须提供成熟的应用层能力以降低开发成本（应对工期）、必须不把核心算法封装在框架黑盒里（应对深度）。经过对 Dify、LangChain、自研全栈三种候选方案的对比分析（见表 3.1），最终选择"Dify 承担应用壳子 + 自研算法独立成服务"的解耦架构。

在这一架构下，Dify 专注做好它最擅长的事——对话编排、知识库管理、工作流配置、多应用切换；而毕设要做透的层次化检索、合规生成、跨域对齐三个算法，以独立 Service 形态通过 HTTP API 与 Dify 通信。这一设计使论文核心贡献在工程上具有三重独立性：可独立评估（不依赖 Dify 即可跑通算法实验）、可单独消融实验（算法服务层的每个子模块都是天然对照组）、可单独开源（算法代码与 Dify 无耦合）。同时，产品端的快速交付完全不受算法迭代节奏的影响。

#### 3.3.2 为何将外部模型层独立成层并标注合规边界

党务数据的合规红线是"数据不出校园"，但 Demo 阶段受 GPU 资源限制，无法在本地部署参数规模约 1.6T 的 DeepSeek V4 模型，只能通过 API 调用外部推理能力。这意味着系统中客观存在一条唯一的跨域数据流——从算法服务层到外部模型层。

与其让这条数据流作为"实现细节"隐藏在代码中、在答辩时被追问才临时解释，不如在架构层面主动将其显式化。将外部模型层以虚线边框 + 异色填充独立画出，实现了三重目的：架构层面——任何看过体系结构图的人都能一眼识别合规边界的位置；工程层面——强制系统在该边界处部署脱敏中间件和审计日志，而非依赖开发者"记得"做脱敏；答辩层面——这条边界本身就是论文中可以展开讨论的设计点，体现设计者对合规问题的主动思考而非被动规避。

#### 3.3.3 为何选择 Qdrant 作为向量数据库

向量数据库的选型直接影响层次化 RAG 的检索质量上限与系统运维成本。选型时系统对比了 Milvus、Weaviate、PGVector、Chroma 与 Qdrant 五个候选方案，按三个维度评估：党建文档特征匹配度（长文本、强结构、元数据过滤需求密集）、Dify 集成成本（是否原生支持、是否需要额外适配层）、答辩友好度（是否为学界/业界认可的主流方案，是否有清晰的技术亮点可陈述）。

最终选择 Qdrant 的核心理由：其元数据过滤能力完善，能够高效支撑层次化 RAG 中按章/节/条做精细化检索的需求——这是本系统向量检索的核心使用模式；单 Docker 容器即可部署，资源开销低，匹配校园网服务器有限的硬件条件；Rust 实现保证了在党建文档库持续增长后的性能裕度；Dify 原生支持，零适配成本接入；社区活跃且定位精准，不会因"功能大而全"造成资源浪费。

#### 3.3.4 Dify 内置知识库与党务 AI 大模型知识库的分工

Dify 自带知识库与自研层次化 RAG 在功能上存在重叠区间，若不做明确分工，将导致两类问题：技术层面，结构化文档被平面化处理后丢失层级信息；运维层面，同一份文档在两边各存一份，更新时容易不一致。

本系统的分工策略清晰且可操作：Dify 自带知识库负责轻量级、平面化内容（FAQ、通知公告、流程手册等无强层级结构的文档），发挥其开箱即用、配置简单的优势；党务 AI 大模型负责需层次化检索的核心党建文档（《党章》《网络行为规范》《中国共产党党员教育管理工作条例》等），发挥自研算法对章/节/条/款结构的深度解析能力。两者共用同一 Qdrant 实例但使用不同 collection，物理资源不重复建设，业务逻辑职责分离。

#### 3.3.5 为扩展模块预留集成接口

通识模块与扩展模块在体系结构上共享算法服务层的基础能力，这一共享不是"恰好能复用"的偶然，而是设计层面主动预留的集成接口。具体而言：Dify 可通过多应用机制为扩展模块新增独立的应用入口，无需另起炉灶；层次化 RAG 和合规生成服务可直接被扩展模块的脚本生成流程调用；跨域对齐服务天然就是扩展模块的核心组件；数据层通过 schema 隔离实现通识模块与扩展模块的数据互不干扰。扩展模块的教师入口采用独立 Web 前端部署，充分隔离党员/书记/教师三类角色的权限边界。

## 4 系统部署拓扑

### 4.1 拓扑总览

系统部署拓扑是将体系结构层面的设计决策落实到物理网络环境中的关键一环。本平台在物理部署形态上采用"三区域 + 合规边界"的清晰结构，把所有组件按其网络位置与合规属性严格划分到三个区域：校园网外公网、校园网边界 DMZ 与防火墙、校园网内私有部署区。这一划分的核心价值在于——把 3.2.5 节体系结构图上那条"数据是否出校园"的抽象边界，转化为部署拓扑图中"请求穿越哪几道防火墙、经过哪些安全节点"的物理落地方案，使合规约束从设计原则变为可操作的网络策略。

### 4.2 三区域划分与合规边界

#### 4.2.1 校园网外（公网）

公网区域汇聚了三类系统需要与之交互的外部参与方：党员手机（党员用户的微信应用所在终端，是系统最高频的使用触点）、微信服务器（腾讯机房，作为消息收发的中转枢纽与公众号能力平台）、支部书记电脑（书记在校外远程办公时的接入终端，通过校园 VPN 安全拨入）。这些设备不是系统的内部组件，但因为系统必须通过它们与最终用户交互，在拓扑图中将其作为外部运行环境完整呈现——这不是"画蛇添足"，而是为了真实展示系统端到端的物理通信链路。

#### 4.2.2 校园网边界（DMZ / 防火墙）

校园网边界由学校防火墙与反向代理 Nginx 联合构成，是整个系统安全防线的咽喉节点，承担两项关键职责。其一，作为公网进入校园网的唯一合法入口，完成 HTTPS 终止、证书管理与端口转发，将所有外部流量安全地转发至内网应用服务器。其二，作为校园 VPN 的接入门户，为书记在校外通过 VPN 拨入后安全访问内网管理后台提供加密通道。Nginx 在此处的角色不仅是一个流量转发器，更是加密边界的守护者——所有跨边界流量在此处完成 HTTPS 终止，内网内部使用 HTTP 通信以降低不必要的加密性能开销。

#### 4.2.3 校园网内（私有部署区，数据合规边界）

校园网内是整个系统的核心阵地，也是数据合规的物理边界。内部按职责进一步分为应用服务器区和数据存储区两个逻辑子区。

应用服务器区基于 Docker Compose 单机部署，运行三个核心容器：Dify 容器（端口 5001，负责应用编排与对话管理）、算法服务容器（基于 FastAPI，端口 8000，内置脱敏中间件，承担层次化 RAG/合规生成/跨域对齐三个子服务）、教师 Web 前端容器（扩展模块专用，端口与部署配置独立管理）。数据存储区运行三类持久化组件：PostgreSQL（端口 5432，存储党员档案与全部业务数据）、Qdrant（端口 6333，存储向量嵌入与层级元数据）、文件存储（保存党建原始文档的 PDF/Word 版本）。

这一区域的网络安全策略严格执行"默认禁止、按需开放"原则。网络出口受学校防火墙严格管控，默认禁止一切主动出站连接；唯一的例外是算法服务容器到 DeepSeek API 的特定 HTTPS 出站白名单——且该链路上的所有请求文本必须先经过脱敏中间件处理。

需要旗帜鲜明地强调："校园网内"的物理边界就是数据合规边界。所有党员的原始 PII 数据（姓名、身份证号、电话、微信 OpenID 等）只在该区域内产生、流转与存储；唯一跨越这条边界的数据流是从算法服务容器到 DeepSeek API 的已脱敏请求文本。这一边界不是文字上的修辞，而是防火墙规则、网络策略、代码审查清单中可以被逐条验证的硬约束。

## 5 系统数据流设计

### 5.1 数据流图分层方法

数据流图（Data Flow Diagram, DFD）是软件工程中久经考验的系统建模工具，用来精确刻画系统中数据如何被产生、加工、存储和消费。它由四类基本建模元素构成：外部实体（矩形，标记系统边界之外与系统交互的人或外部系统）、加工（圆形或圆角矩形，代表系统内部的数据处理过程）、数据存储（开口矩形或双横线，代表数据的持久化容器）、以及连接它们的数据流箭头（代表有向流动的数据内容）。

本系统采用分层 DFD 的方法逐级展开系统的数据处理逻辑。0 层（顶层/上下文图）采用高度抽象视角，将整个系统压缩为单一加工节点，只刻画系统与外部实体之间的全部输入输出关系——它在最高层面回答一个根本问题："这个系统到底跟外界交换什么数据？"1 层将 0 层中的单一加工分解为系统内部的若干子加工，并将所有数据存储显式画出——它回答两个工程层面的关键问题："数据在系统内部如何流转、经过哪些处理环节？""业务数据最终存到哪里、由谁写入、由谁读取？"

本设计文档画到 1 层为止，不再继续向下分解至 2 层。理由是 1 层已经完整揭示了五个子加工的职责边界、数据流向与存储分配，足以支撑后续软件实施阶段的接口定义与模块划分——继续向下分解将陷入具体实现的细节，反而不利于设计文档保持恰当的抽象层次。

### 5.2 顶层数据流图（0 层）

0 层数据流图将整个本平台系统抽象为单一加工节点，全面刻画其与外部环境的数据交换全景。系统识别出四类外部实体：党员、支部书记、微信平台、DeepSeek API。前两类是系统的最终使用者，以实线连接表示直接交互关系；后两类是系统在运行时必须依赖但不属于系统主体的外部系统，以虚线连接表示——这一虚实区分与跨边界数据流的合规标注形成呼应，共同构成数据流图层面的合规表达。

### 5.4 数据流设计的关键点

#### 5.4.1 把智能问答（P4）单独作为一个加工

从纯业务视角看，智能问答完全可以归入"学习管理"的子功能——毕竟党员的提问行为天然属于学习场景。但本设计选择将 P4 提升到与 P1 平级、独立成为一个加工，这一决策的依据是：智能问答承载的是本毕设最核心的研究产出——层次化 RAG 算法。把它独立成加工，使其在数据流图中拥有与其他业务加工同等的可见度与独立性，便于在后续详细设计、接口定义与论文撰写中将其作为独立的研究单元来处理。这不是"过度设计"，而是"研究导向的设计表达"——让数据流图本身就能讲清楚"这个系统的学术贡献在哪里"。

#### 5.4.2 跨边界数据流的显式标注

1 层数据流图中，P3 写作辅助与 P4 智能问答到 E4 DeepSeek API 的两条数据流采用红色虚线特殊标注，并附文字说明"脱敏后的提问 + 上下文""脱敏后的写作要点"。这一标注实现了合规边界在三个设计视图中的一致性表达：体系结构图用虚线框 + 异色标注外部模型层的边界属性；部署拓扑图用防火墙与 DMZ 标注网络层面的合规边界；数据流图用红色虚线标注数据流动层面的合规边界。三张图从三个维度共同回答同一个问题——"数据是否出校园？"—答案在任何一张图上都明确可见。

#### 5.4.3 积分计算（P5）采用事件驱动而非请求驱动

P5 与其他四个加工存在本质性的衔接模式差异。P1、P2、P3、P4 均由用户请求直接驱动——党员发起或书记下发后即刻执行。P5 则不同：它不直接接收任何用户请求，而是由其他加工产生的"积分事件"驱动。在数据流图上表现为 P1/P2/P3 向 P5 发出积分事件流（完成学习/答对题目/写作完成），P5 接收事件后写入 D5 积分日志库。

这一事件驱动设计实现了积分逻辑与业务逻辑的彻底解耦。业务模块只需要发出"我做了什么"的事实事件——它不需要知道积分规则是什么、当前积分是多少、不同动作各值几分。P5 独立负责接收事件、按规则计算积分、写入日志。当积分规则需要调整时（如"学习一篇材料从 5 分改为 8 分"），只需要修改 P5 的规则配置，所有业务模块代码不受影响。这一设计与积分系统采用事件溯源模式的决策形成完整的逻辑闭环。

## 6 数据库概念设计与数据字典

### 6.1 数据库概念设计概述

#### 6.1.1 设计原则与命名约定

数据库设计是软件设计文档中颗粒度最细、对后续编码质量影响最直接的章节。表结构一旦建好并写入生产数据，后续变更的成本将成倍增长。为确保数据库结构经得起业务演进的考验，本系统的数据库设计严格遵循以下五条原则。

**a. 面向业务实体建模，而非面向页面或接口建模。** 数据库结构反映的是党务工作中的真实业务实体（党员、支部、学习材料、任务、答题记录等）及其关系，而不是某个具体页面或 API 接口的数据组装形态。这一原则的价值在于：前端页面会改版、接口会重构，但"一个党员属于一个支部""一次学习任务关联多份材料"这些业务事实是稳定的。面向实体建模使数据库结构在应用层频繁变化时保持稳固。

**b. 命名约定统一为 snake_case。** 所有字段名采用小写字母 + 下划线分隔的形式（如 `birth_date`、`branch_id`、`created_at`），实体名（表名）采用 PascalCase（如 `Member`、`LearningMaterial`、`PointRecord`）。这一约定与 PostgreSQL 的主流 ORM（如 SQLAlchemy）的默认命名行为天然兼容，避免"数据库里叫 `birth_date`，代码里要映射成 `birthDate`"的额外心智负担。

**c. 主键统一为自增 BIGINT。** 所有业务表使用代理主键 `id`（BIGINT 自增），坚决不使用业务字段作为主键。身份证号看似是党员表的"天然主键"，但当合规要求需要对身份证号做加密存储或脱敏替换时，所有引用该字段的外键关系将全部崩塌。代理主键以一层间接性换来了对业务字段变更的完全免疫。

**d. 时间字段统一使用 TIMESTAMP，日期字段使用 DATE。** 需要精确到秒的时间戳（创建时间、更新时间、答题时刻等）使用 TIMESTAMP 类型；只表示日期而无时间精度需求的字段（出生日期、入党日期、发布日期等）使用 DATE 类型。所有 `_at` 后缀字段（`created_at`、`updated_at`、`completed_at`）均为 TIMESTAMP。

**e. 多对多关系一律通过关联表实现。** 不使用 PostgreSQL 的数组类型或 JSON 字段来存储关系——这些快捷方式在数据量增长后会导致查询性能急剧下降，且无法建立外键约束保证引用完整性。本系统中的四组多对多关系（任务-材料、任务-党员、考试-题目、考试-党员）分别通过 `TaskMaterial`、`TaskAssignment`、`ExamQuestion`、`ExamAssignment` 四张关联表规范化实现。

### 6.2 E-R 图与实体清单

#### 6.2.1 E-R 图整体说明

本系统的 E-R 图采用 Crow's Foot 表示法（乌鸦脚记法）绘制，这是数据库设计中表达实体关系的工业标准记法。每个矩形代表一个实体（对应一张数据库表），矩形内列出实体的核心属性（字段名 + 类型 + 主外键标识）。矩形之间的连线代表实体间的关系，连线两端的符号精确表达关系基数：单竖线代表"一"、乌鸦脚（三叉）代表"多"、空心圆代表"零"（可选参与）。

E-R 图完整覆盖 P0 阶段所需的全部 15 张表。由于实体数量多、关系密集，本图按业务主题对实体进行了空间分组以提升可读性：Member 与 Branch 占据图的中心位置，作为基础实体被其他所有业务实体广泛引用；学习类、自测类、写作类、积分类实体各自聚集在对应主题区域，通过外键箭头与中心的基础实体相连。读者可以一眼识别出系统的数据"重心"在哪里——党员（Member）与支部（Branch）是数据模型的骨架，其他所有业务数据都围绕它们展开。

### 6.3 数据字典

本节是数据库设计的核心交付物，对全部 15 张表逐一给出实体说明与字段级数据字典。每张表的呈现方式遵循"先讲清为什么、再列清是什么"的原则：一段实体说明讲清这张表存什么数据、关键字段的设计考虑、为什么这样设计；一张字段定义表（字段名 / 数据类型 / 约束 / 默认值 / 中文说明，五列）提供精确的字段级定义。

字符串字段的长度按用途分档约定，保证既不浪费存储也不限制业务：短标识类（角色、状态、类型等枚举值）使用 `VARCHAR(32)`；中等文本（姓名、标题等）使用 `VARCHAR(100)`；长文本（描述、链接、标签等）使用 `VARCHAR(255)`；超长文本（题目内容、AI 草稿等）使用 `TEXT` 类型不设限；身份证固定使用 `VARCHAR(18)`；手机号使用 `VARCHAR(20)` 兼容国际号码；微信 OpenID 使用 `VARCHAR(64)`。

#### 6.3.1 基础类（2 张）

**Member（党员表）。** 存储党员基础档案信息，是系统中引用最密集、业务关联最广泛的核心实体。该表的字段设计体现三重考虑。其一，基础身份字段（`name`、`id_card`、`phone`、`wechat_openid`、`gender`、`birth_date`）覆盖党员档案的标准内容项，与组织部门要求的党员信息采集表对齐，确保数据录入时字段不缺失。其二，党务专属字段（`join_party_date`、`party_status`、`role`）精准体现系统的党务领域特征，将通用用户表与党员表区分开来。其三，该表刻意不设 `total_points` 字段——党员的总积分通过对 PointRecord 表执行 `SUM` 聚合实时计算，这是事件溯源模式在数据模型层面的直接体现（设计理由详见 8.2.1 节）。

`party_status` 字段取值覆盖发展党员全流程的六个阶段（申请人/积极分子/发展对象/预备党员/正式党员/已转出）。即使 P0 范围内实际只用到其中两种状态值（预备党员/正式党员），全量保留状态枚举是为 P1 发展党员模块预留平滑扩展空间——届时只需前端开放对应状态的筛选选项，无需对数据库做结构变更。`role` 字段区分 `admin`/`secretary`/`member` 三种角色，对应系统管理员、支部书记、普通党员三类用户。

**LearningMaterial（学习材料表）。** 存储党建学习材料的完整元数据。核心设计在于 `type` 与 `category` 的双维度分类体系：`type` 按材料形态划分（文章/视频/文件/外链），`category` 按内容主题划分（理论/政策/时事/党史/其他）。双维度交叉筛选使党员可以灵活定位材料——既能"只看视频类型"，也能"只看时事政治类"，或组合筛选"时事政治类的视频"。`content_url` 字段存储材料的实际访问地址或文件路径。该表与 Qdrant 中的向量切片通过 `id` 建立逻辑关联，但 Qdrant 中的向量元数据不在本表内重复存储——遵循"每种数据存在最适合它的数据库里"的原则。

**WritingRecord（写作记录表）。** 存储党员每次使用写作模块的完整记录，字段序列精确反映"轻版"模式的三步流程：`user_input`（党员填写的写作要点）→ `ai_draft`（大模型基于模板与要点生成的初稿）→ `final_content`（党员在初稿基础上编辑后的最终版本）。`status` 字段当前仅使用 `draft` 和 `saved` 两个状态值，体现"只在辅助层面工作、不进入组织审批流程"的 P0 范围决策。该字段保留为 `VARCHAR(32)` 而非 `BOOLEAN` 的设计意图明确——未来扩展为完整工作流时，只需增加状态值（如 `submitted`/`reviewed`/`rejected`），无需对表结构做任何变更。

**表 6.15 WritingRecord（写作记录表）字段定义**

#### 6.3.5 积分类（1 张）

**PointRecord（积分记录表）。** 这是整个数据模型中最能体现设计思想的一张表。它采用事件溯源（Event Sourcing）模式实现——党员的每一次积分变动都生成一条不可变的新记录，而不是在 Member 表上维护一个不断被覆写的 `total_points` 字段。Member 的当前总积分由一条简单的聚合查询 `SELECT SUM(points) FROM PointRecord WHERE member_id = ?` 实时计算得出。

这一设计为系统带来了三项工程收益，而这三项收益在传统"字段累加"模式下都无法实现。（1）可追溯：党员提出"我这 50 分是怎么来的"时，系统可以精确列出每一笔积分的来源、时间和事由，而不是只能回答"你现在的积分是 50"。（2）可撤销：当发现积分规则配置错误导致一批党员多加了分时，可以通过追加负值冲账记录来纠正，所有历史记录完好保留，审计线索不丢失。（3）可分析：按 `action` 和 `source_type` 字段做分组聚合，可以回答"学习类活动贡献了多少积分""自测类活动贡献了多少积分"等精细化运营问题——这些数据是支部书记优化积分规则激励方向的事实依据。

`source_id` 与 `source_type` 两个字段构成"多态外键"——它们联合指向产生该条积分的源记录。`source_type` 取值为产生积分事件的实体名称（如 `LearningRecord`/`TaskAssignment`/`AnswerRecord`/`WritingRecord`/`ExamAssignment`/`Manual`），`source_id` 为该实体表中对应记录的主键值。

## 7 课程思政短视频脚本生成系统的算法设计

### 7.1 扩展模块定位与目标

课程思政短视频脚本生成系统是本平台的扩展模块，是通识模块能力向"党员理论学习与教师专业课融合"场景的战略延伸。在高校党建的实际工作中，长期存在一个结构性难题：党员的理论学习与教师的教学业务各自运转，如同两条并行的轨道，缺乏有机的交汇点——这就是俗称的"两张皮"现象。

本扩展模块正是要打通这两条并行的轨道。模块以党务 AI 大模型的三个子服务（层次化检索、合规生成、跨域对齐）为算法底座，聚焦"党员理论域 ↔ 课程教学域"的跨域融合这一核心技术问题，用算法能力将时政理论自然融入教师的专业课教学场景，让理论学习成果转化为可见的教学产出。

本扩展模块的核心目标是：坚持把本学年共产党员应知应会理论学习，与教师日常教学、课堂育人、师德师风、教研教改等实际工作深度融合、一体推进，杜绝理论学习与教学工作"两张皮"，做到以理论铸魂、以学习赋能、以实干践行初心使命。

本扩展模块在本毕设中独立成章，章节内重心放在算法设计层面，具体算法在 7.4 节展开。

### 7.2 六项原则约束体系

扩展模块的脚本生成不是"自由创作"，而是在课程思政教学的六项原则严格约束下的"受控生成"。这六项原则来自吴老师提供的教学规范文件，在系统中被提升为第一准则——在算法层面建模为生成约束条件，任何一条生成的脚本都必须至少满足其中一项原则的要求，且不违反任何一项原则的精神。

**a. 与学科专业相关性原则。** 结合课程所归属和服务的学科与专业的形成背景、发展历程、现状和未来趋势，特别是所涉及的重大工程和科学技术发展成果，挖掘其中所蕴含的使命感、责任感、爱国精神、奋斗精神、开拓精神等思政元素。

**b. 符合职业发展要求原则。** 结合不同专业的人才培养特点以及学生未来所从事工作的职业要求，从职业素养养成的角度，有针对性地挖掘课程所蕴含的育人元素，增强育人的针对性和实效性，提升学生职业发展能力。

**c. 结合热点时事对比原则。** 从国际国内两个大局热点时事资源背景中挖掘课程所蕴含的思政元素，教会学生用正确的立场观点方法认识并分析问题，让学生深刻认识世界、理解中国、增强民族自信心和社会责任感。

**d. 历史与现实分析原则。** 从大师的成长道路到校友的成功经验，到教师个人经历中的值得借鉴的经历，甚至社会上一些失败教训和警示性问题。讲好历史与现实的故事，引导学生从中发掘价值观、形成正确的判断事物标准和价值追求。

**e. 注重家国情怀培养原则。** 根据教学需要，选取改革发展稳定、内政外交国防、治党治国治军各方面取得的巨大成就，以及中国特色社会主义在本地区的实践成果进行案例撰写，积极传播和弘扬中华优秀传统文化、革命文化和社会主义先进文化。

**f. 注重实践体验挖掘原则。** 选取学生在实践过程中能够通过身体力行深刻感悟的思政元素，使之内化为学生的精神追求、外化为学生的自觉行动。思政元素包括制度敬畏与自觉遵守、环境保护、珍惜生命、客观严谨细致的科学精神、团队协作、发现与质疑、探索精神、创新思维等。

### 7.3 系统工作流

扩展模块的端到端工作流设计清晰，每一步都有明确的输入输出：

```
输入（三路）：
├─ 党员理论（本学年应知应会内容，如二十大精神、党章修订内容等）
├─ 教师输入（文字提纲 / 课件 PPT·PDF / 知识点列表，三种形态可组合）
```

视频生成环节不自研——调用即梦或类似第三方 AI 视频引擎完成。已用即梦成功跑通 15 秒 demo，端到端可行性已获验证。研究贡献聚焦在"脚本生成算法"上，视频渲染本身不是研究产出。

#### 7.4.1 多源输入归一化

教师输入的形态多样性是系统面临的第一道处理门槛——有的教师习惯于写简短的文字提纲，有的教师有现成的 PPT 课件，有的教师直接给出结构化的知识点列表。归一化模块正是为跨越这道门槛而设计：它负责将三种形态、多种格式的输入统一转换为系统的内部标准表示。处理过程包括文本内容提取（从 PPT/PDF 中抽取纯文本）、知识点结构识别（从提纲或列表中识别出知识点边界与层级关系）、学科领域标签标注（自动识别教学内容所属的学科领域）。归一化后的内部表示为后续的跨域对齐算法提供了干净、统一、结构化的输入。

#### 7.4.2 跨域语义对齐

跨域语义对齐是扩展模块的算法核心，也是本毕设在研究层面最具创新潜力的组件。它面向一个真实的自然语言处理挑战：党员理论域（以党建文献、政策文件、理论学习材料为代表）与课程教学域（以专业课教材、教学大纲、知识点体系为代表）分属两个话语体系，用词习惯、概念体系、表达逻辑都有显著差异。传统的关键词匹配方法在这两个域之间几乎完全失效。

跨域语义对齐的目标不是做简单的关键词映射，而是找到两个域之间的"融合点"——即党员理论中的哪些内容（如"科技创新""奋斗精神""家国情怀"等思政元素）可以与教师专业课中的哪些知识点（如某个技术案例、某段学科发展史、某个工程伦理讨论）形成自然、不牵强、有教学价值的结合点。这些融合点就是课程思政教学案例的原材料。

#### 7.4.3 六项原则约束的脚本生成

脚本生成组件是整个扩展模块的输出端。它在六项原则的约束框架下，基于跨域对齐产出的融合内容，生成结构化的分镜故事脚本。六项原则在此处不是装饰性的"指导思想"，而是在算法层面被建模为可操作的生成约束——生成的脚本必须至少明确满足其中一项原则的要求（如"体现了学科专业相关性"），且不违反任何一项原则的基本精神。

脚本的输出格式是结构化分镜脚本，每一镜包含画面描述、旁白文本、配乐提示、时长建议等字段。这些字段结构是基于已跑通的即梦 demo 反推确定的——不是凭空设计，而是从实际可用的视频生成引擎的输入格式倒推而来，确保输出脚本可以直接导入引擎而不需要人工二次转换。

### 8.2 补充论述

#### 8.2.1 积分系统采用事件溯源模式

积分系统的数据模型在设计阶段有两条相互竞争的候选路径。路径一（状态模式）：在 Member 表中增加 `total_points` 字段，每次积分变动时对该字段执行 `UPDATE ... SET total_points = total_points + N`。路径二（事件溯源模式）：建立独立的 PointRecord 日志型表，每次积分变动新增一条记录，Member 的总积分由 `SELECT SUM(points) FROM PointRecord WHERE member_id = ?` 实时计算。

路径一实现简单、查询直接，但有一个致命缺陷：它只保留"现在积分是多少"这一最终状态，而丢失了"积分是如何变成现在这样的"全部过程信息。路径二以额外的 SUM 查询开销，换取了三个路径一完全无法提供的能力。

本系统坚定选择路径二。核心理由三个层层递进。第一层——可追溯：党员质疑积分时可以逐笔列出来源，透明公开是党务工作的基本要求。第二层——可纠错：积分规则出错时通过追加负值冲账记录来纠正，所有历史记录完整保留，审计线索不中断。第三层——可分析：按活动类型分组统计积分贡献，为支部书记优化激励策略提供数据支撑。从工程成本看，路径二带来的额外开销是查询时多执行一次 SUM——在 `(member_id, created_at)` 复合索引的加持下，这个开销对学院级数据规模完全可以忽略。用几乎为零的额外成本换取数据不可变性的全部收益，这是本系统最值得讲清楚的一个设计决策。

#### 8.2.2 写作模块只做 AI 辅助轻版，不做工作流

写作模块在项目 V1 设想阶段曾有一个"完整组织流程版本"的蓝图：党员撰写思想汇报 → 提交支部 → 书记审阅 → 给出反馈意见 → 党员修改 → 归档留存。这一工作流在党务现实中确实存在，功能上也完全合理。

但在 V2 阶段经过审慎权衡，本毕设范围内明确决策只做"轻版"——即"用户输入要点 → AI 生成草稿 → 用户保存或导出"的单向辅助链路，不进入组织审批流程。这一决策有三层递进式考虑。

第一层是合规层面。工作流版意味着把党员的思想汇报、民主评议自评等敏感文书放在系统中流转——这些文书涉及党员的政治表态和个人思想，其流转规则需要与学院党委逐一确认才能设计稳妥。在毕设阶段尚未与学院党委建立正式对接机制的情况下，贸然实现完整工作流存在合规风险。

第二层是定位层面。本系统定位为"Agent"——其核心价值在于用 AI 能力辅助党员完成任务，而不是替代或重构党组织的既有工作流程。轻版精准契合了"辅助"的定位边界。

第三层是工程层面。轻版可在 P0 阶段完整交付并上线使用，党员立刻可以获得 AI 辅助写作的价值。数据库层面的兼容性已提前预留：WritingRecord 表的 `status` 字段使用 `VARCHAR(32)` 而非 `BOOLEAN`，未来扩展工作流时只需追加状态枚举值，表结构无需变更。

#### 8.2.3 E-R 实体命名采用英文，论文中用实体说明表对照

E-R 图与数据字典中的实体名称统一使用英文（Member、Branch、LearningMaterial 等），不进行中文化命名。这一选择的工程依据是：英文命名与 SQL 语法、ORM 框架、代码变量名三者天然兼容——数据库中叫 `Member`，代码中就是 `class Member`，SQL 中就是 `SELECT * FROM Member`，全程无需翻译映射。同时，英文命名也是主流数据库设计教材与企业开发规范的通用做法，在答辩时不会因为"命名不规范"被挑刺。

中文论文的阅读便利性问题通过"实体说明表"机制解决：在数据字典章节中，每张英文命名的表都附有一整段中文实体说明，讲清这张表对应党务工作中的哪个业务概念、存什么数据。读者不需要在"Member 是什么"上做任何猜测。

#### 8.2.4 层次化 RAG 拆为五个子模块的设计

层次化 RAG 是本毕设的主算法。在算法服务内部设计上，它被拆解为五个子模块：结构化解析器、层次化切片器、元数据增强器、多层级检索器、检索结果重排器。这一拆分不是为了让模块数量"看起来更多"的任意切分——五个子模块一一对应层次化 RAG 流水线中五个可以独立替换、可以独立评估的处理阶段。

从工程维度看，每个子模块有明确的输入输出接口，可以独立编写单元测试，也可以独立用更优算法替换而不影响前后模块。从研究维度看，五模块拆分直接为消融实验提供了天然的对照组矩阵——论文中可以设计"完整五模块 vs 去掉元数据增强器 vs 去掉重排器 vs 用单层平面检索替换多层级检索器"等多组消融配置，定量评估每个子模块对最终检索精度和生成质量的独立贡献。这种"设计即实验设计"的模块划分方式，使得算法设计与实验验证在同一个框架内自然衔接。

## 9 实施约束与待确认项

本章列出当前软件设计中，部分依赖于学院或学校层面进一步对齐才能最终落定的关键事项。这些事项不构成对整体设计方案成立性的威胁——无论它们的最终决策结果如何，本设计的核心架构与模块划分都能适配。但它们的最终形态会影响部署阶段的具体配置参数，因此需要在实施前逐项确认。

### 9.1 公众号主体归属

系统以微信公众号（服务号）作为面向党员的日常入口，这一设计假设了一个前提：存在一个可用的、具备学校主体资质的微信公众号。当前有两种可行方案。方案一：挂载到学院已有的官方公众号，以新增菜单项与功能模块的方式接入——优势是无需重新申请、审核和备案，上线速度最快；劣势是功能入口受限于学院公众号的菜单布局和内容规划。方案二：以教师第一支部名义向学院党委申请独立的服务号——优势是功能入口独立、品牌清晰、运营自主；劣势是申请与备案流程较长，且需要学院党委审批。

两种方案在系统接口层面的设计是一致的——无论公众号是"学院号的菜单"还是"支部独立号"，微信服务器与系统后端的通信协议不变。只是部署阶段需要替换公众号的 AppID 与 Token 等配置值。最终的方案选择需要在与学院党委沟通后做出——这个选择本质上是运营决策而非技术决策，本设计文档对两种方案保持兼容。

### 9.2 校园网内部署资源

系统在校园网内的部署需要一台具备充足资源的物理或虚拟服务器作为应用与数据存储的宿主机。当前对硬件资源的最低预估为：4 核 CPU、16 GB 内存、500 GB 存储空间，不需要 GPU（Demo 阶段大模型推理走外部 API，本地不承担推理负载）。

需要提前预判的是：如果未来切换到本地化部署模型的方案（即外部模型层回归校园网内），硬件需求将显著变化——至少需要额外协调一张 24 GB 或以上显存的 GPU。具体的服务器获取路径（学校信息中心分配虚拟机？学院自有机房？导师科研经费采购？）需要在与学院或信息中心沟通后确定。在设计上，本系统所有组件均为容器化部署，无论最终服务器以什么方式获取，部署流程不受影响——拿到 IP 和 SSH 账号就能上线。

### 9.3 合规边界的最终形态

当前设计中，跨合规边界的数据流是"算法服务容器 → DeepSeek API"，它的合规前提是：Demo 阶段允许将脱敏后的请求文本发往境内但非校园网内的商业 API 服务。生产阶段的合规要求可能比 Demo 阶段更严格——"数据不出校园"如果被解读为"不出校园网物理边界"，则当前的外部模型层方案需要调整。

本设计文档对此已经做好了架构层面的预案。由于体系结构中将外部模型层独立成层、与算法服务层仅通过 HTTP API 松耦合，这一切换在工程上代价极低：无论是切换到本地部署的开源模型（如 Qwen 32B）、还是接入学校已有的私有大模型服务，都只需要替换外部模型层的实现，算法服务层与上层应用零改动。换句话说，合规边界的物理位置可以变化，但分层结构恒稳——这是"为变化而设计"的典型案例。

### 9.4 数据集与测试集来源

系统中三类数据需要在实施阶段持续积累与补充，它们共同决定了系统从"能跑"到"好用"之间的距离。

第一类是党建文档库的内容。需要陆续录入《党章》《网络行为规范》《党员教育管理工作条例》等核心党建文件，以及学院党委发布的相关规章制度与学习材料。文档库的完整度直接影响层次化 RAG 的检索覆盖面和智能问答的回答质量。

第二类是算法评估用的标注测试集。层次化 RAG 与合规生成两个算法都需要"问题—标准答案—相关条款"三元组形式的标注数据来做定量评估。当前规划的构建路径是：以 12371 共产党员网党务问答板块中的真实党员提问为种子数据，经过人工筛选与标注后，辅以 LLM 辅助扩充，形成规模适中、质量可控的测试集。

第三类是党员真实使用数据。这部分数据只能在系统试点上线后由实际使用自然产生——学习记录、答题记录、写作记录、问答日志等。它是后续算法迭代优化最宝贵的数据源，但其积累需要时间，急不得。

## 10 结论

本设计文档对"基于 Dify 的高校 AI 党务平台"进行了系统性的完整软件设计，深度覆盖了系统功能设计、体系结构设计、部署拓扑规划、数据流设计、数据库概念设计与数据字典、以及扩展模块的算法设计六个核心维度。

在通识模块方面，本平台构建了"Dify 应用编排 + 党务 AI 大模型算法服务"的分层解耦架构，以微信公众号为党员日常入口，以 Web 管理后台为书记管理阵地，全面覆盖学习、自测、写作、会议、发展党员、台账、系统管理七个功能模块。数据库设计以事件溯源模式为核心亮点，提供了包含 15 张表的完整数据字典，从实体关系到索引策略均给出了精细化的设计论证。在数据合规方面，本平台以"数据不出校园"为最高约束，在体系结构图、部署拓扑图、数据流图三个设计视图下对合规边界进行了一致性标注与逐层落实——架构层的抽象边界在部署层转化为防火墙规则，在数据流层转化为脱敏标注，三图合一构成完整的合规论证链条。

在扩展模块方面，本平台设计了课程思政短视频脚本生成系统，以六项教学原则为硬约束，通过跨域语义对齐打通"党员理论域"与"课程教学域"之间的壁垒，将理论学习成果转化为可驱动视频引擎的结构化分镜脚本。该模块在设计层面完整呈现——算法、工作流、接口、数据结构均有明确定义；在实施层面精简验证——聚焦端到端链路，以 15 秒 demo 证明可行性。

后续工作将严格按照 P0 → P1 → P2 的优先级顺序推进系统实施，以"这学期让真实党员用上"为核心目标，让设计文档从纸面走向现实。
