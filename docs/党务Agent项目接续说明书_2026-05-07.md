## 二、必须遵守的协作规则

### 规则 1:决策权归用户
**用户做决策(全做的目标范围、风格选择、节奏快慢) → Claude 出实现**。不替用户刹车,不替用户喊累。

### 规则 2:用户必须能讲清"为什么这么做"
所有产出物都要让用户答辩时能讲清楚——不能黑盒输出。

### 规则 3:主线纯粹性
此项目对话只聊党务 Agent,不带入副业(API 中转站)、其他兴趣(德州扑克、命理)、其他课业。

### 规则 4:跟吴老师对接的回复用"接住 + 复述确认 + 下一步动作"模式

### 规则 5:党建领域知识
用户**不是党员,业务认知薄弱**,正在通过 12371 / 学习强国补常识。涉及业务决策时先铺背景。

### 规则 6:不替用户喊累、不替用户刹车
用户没明说累的时候,**不主动建议"今天到此为止"**。但**信息层面的"暂停 + 整理"仍然有用**(比如把决策固化成文档)。

### 规则 7:节奏跟"60-90 天落地"对齐
优先级判断标准:**对"这学期落地"的贡献度 > 对"未来论文"的贡献度**。学院派"先打基础再创新"的惯例不适用。

### 规则 8(Claude 自查项)
不要因为信息量大就建议"分批做"、"晚一点做"、"今天先停"——这些会被解读为推迟进度。**信息量大不是分批的理由,一次给完是默认动作**。

## 七、用户的沟通风格 + 协作模式

### 用户表达特征
- **简短直接**(常用一两个词回复:"OK"、"继续"、"这一段 OK")
- **不喜欢被反复确认**——"快给我写"、"听指令就行"是常见指令
- **会主动 dismiss 询问**(把按钮关掉表示"等下,先不答")——这是合法表达,不是消极
- **会直接指出 Claude 的问题**(比如"你又在拖我进度")——这种反馈要正面接住,不绕

### 用户偏好的输出模式
- **决策选项用 ask_user_input_v0 工具**(选项 2-4 个,标签短)
- **重要产出用 markdown 文档**,放 outputs 目录
- **不要无意义的安慰话/总结话/长 preamble**
- **对比展示比单方案更受欢迎**——"对照原文 vs 改写版"、"两版微信" 之类

### 用户跟老师沟通的模式
- 微信沟通为主
- 用"接住 + 复述确认 + 下一步动作"模板
- 不打扰老师做决策(避免反复请示)
- 同步进度时**报方法和方向,不报过程细节**
