# **一、技术决策**

## **决策 1.1:整体架构 = Dify(应用层) + 自研算法服务(研究层) + 微信公众号(用户入口)**

**决定了什么:**

- 应用层用 Dify(开源、私有部署、知识库/工作流/对话编排开箱即用)
- 算法层独立部署成 Service,Dify 通过 HTTP API 调用
- 用户入口是微信公众号(服务号),不是 Web 应用、App 或小程序

**为什么:**

- 纯 Dify:产品快但算法被封装,毕设深度不够
- 完全自研:深度够但工期紧、产品落地慢
- Dify + 自研算法:两线并进,既能落地又有研究空间(被吴老师认可)
- 微信公众号:党员使用门槛最低,符合现有工作习惯(微信群)

**已排除的方案:**

- Coze:数据走字节服务器,违反"私密文件"原则;且工作流复杂度撑不住
- 完全自研 RAG:工期不够;不必重复造轮子
- 小程序/App 入口:开发成本高,不符合党员使用习惯

## **决策 1.2:大模型 = DeepSeek V4(Demo 阶段)**

**决定了什么:**

- Demo 阶段用 DeepSeek V4 Flash(极便宜)+ Pro(复杂任务),走官方 API
- 党员真实数据(姓名/身份证等 PII)在送入模型前必须脱敏

**为什么:**

- V4 是国产 SOTA、Agent 能力强、百万上下文、价格便宜(Flash 比 Pro 便宜约 12 倍)
- 走官方 API 比本地部署省 GPU 钱(本地跑 V4-Pro 1.6T 参数学校给不起 GPU)
- 生产环境的合规方案推迟到 8-9 月再决策(看真实合规要求)

## **决策 1.3:毕设核心算法 = 层次化 RAG(主) + 合规生成(次1) + 跨域对齐(次2/扩展)**

**决定了什么:**

- 主算法:层次化检索增强生成,做扎实——这是论文核心章节
- 次算法 1:政治表述合规性约束生成,作为工程贡献和论文第二章节
- 次算法 2:跨域语义对齐,作为论文"未来工作"或"扩展研究",留接口给教学 agent

**为什么:**

- 三个算法都做透 = 13-17 周,8 个月毕设周期不够
- 层次化 RAG 跟党务场景最契合(党建文件结构性强,平面切片丢信息)
- 合规生成是工程必需(涉政内容审核必须过),顺便做出研究价值
- 跨域对齐更适合教学 agent,本毕设做初步探索就好

## **决策 1.4:开发节奏 = 双线并进,产品 50% / 算法 50%**

**决定了什么:**

- 从大三下到大四下答辩,两条线时间各占一半
- 5-6 月聚焦产品 MVP(应用线),7-8 月暑假主算法实验(研究线),9-12 月并行,2027 年初论文+答辩

**为什么:**

- 只做产品 → 毕设无算法深度,答辩撑不住
- 只做算法 → 没有真实落地,产品和大创立项不成立
- 双线并进是同时满足吴老师"实际价值"和毕设答辩的唯一路径

## **决策 1.5:向量数据库 = Qdrant(2026 年 4 月 27 日新增)**

**决定了什么:**

- 选 Qdrant 作为向量数据库,不选 Milvus/Weaviate/PGVector/Chroma

**为什么:**

- 党建文档特征(长文本、结构化强、持续增长)+ 元数据过滤需求 → Qdrant 性能和功能匹配
- 单 Docker 容器轻量部署 → 校园网服务器资源有限可承受
- Dify 原生支持 → 零集成成本
- Rust 写性能好,数据增长不慌
- 答辩友好——主流且不大材小用(Milvus 对学生项目过重,会被问"真的需要这个量级吗")

## **决策 1.6:层次化 RAG 的具体实现路径(2026 年 4 月 27 日新增)**

**决定了什么:**

层次化 RAG 服务由 5 个子模块构成:
1. 结构化解析器 — 识别党建文档的章/节/条/款结构
2. 层次化切片器 — 按结构切片,生成带元数据的切片
3. 元数据增强器 — 用大模型为每个切片生成"摘要/关键词/关联条款"
4. 多层级检索器 — 实现"粗检索→精检索→扩展检索"流水线
5. 检索结果重排器 — 根据元数据相关性重新排序

**为什么:**

- 党建文件结构性极强(章/节/条/款),平面 RAG 会丢失层级关系和跨条款引用
- 这五个模块是论文消融实验的天然对照组(去掉哪个看效果下降)
- 跟 Dify 默认平面 RAG 形成 baseline 对比

## **决策 1.7:Dify 知识库 vs 自研算法服务知识库的分工(2026 年 4 月 27 日新增)**

**决定了什么:**

- Dify 自带知识库:放轻量级、平面化的内容(FAQ、简单通知)
- 自研算法服务:处理需要层次化 RAG 的核心党建文档
- 两者**共用 Qdrant 实例,但用不同 collection**

**为什么:**

- 不重复建数据库,节省资源
- 业务逻辑层面隔离,符合"职责分离"原则
- 这个细节在体系结构图里能体现设计深度

# **二、产品决策**

## **决策 2.1:本期范围 = 党务 Agent(通识模块),不并行做其他 agent**

**决定了什么:**

- 本毕设只做党务 agent 一个应用
- 课程思政融合(教学 agent)在本毕设中只作为算法的"扩展研究",不做完整应用
- 架构上为教学/学习/科研 agent 留接口,但不实现

**为什么:**

- 吴老师明确说"先落地通识模块,扩展模块目前只是思想"
- 另外两个 agent(教学/学习)归吴老师明年带的其他学生
- 本毕设范围必须收敛,否则做不完

## **决策 2.2:模块优先级 = 学习 P0 / 自测 P0 / 写作 P0 / 会议 P1 / 发展党员 P1 / 台账 P2**

**决定了什么:**

- P0 模块必须完成,是 MVP 范围(5-6 月)
- P1 模块争取完成,7-8 月暑假冲刺
- P2 模块视情况砍——如果时间不够,不做台账模块

**为什么:**

- 学习/自测/写作是党员日常使用频次最高的三件事
- 会议、发展党员主要服务支部书记,频次低但价值高
- 台账是数据呈现层,模块多了再做意义大,前期可以用简单导出代替

## **决策 2.3:数据合规 = 数据不出校园(生产期)**

**决定了什么:**

- Dify、算法服务、PostgreSQL 部署在校园网内
- Demo 阶段:党员数据脱敏后走 DeepSeek API
- 生产阶段:与学校对齐合规要求后再决定本地化方案

**为什么:**

- 党务数据涉及党员档案、组织内部资料,合规红线
- 不能直接用境外 API、不能用商业 SaaS 平台
- 这是吴老师强调的"私密文件"原则

## **决策 2.4:写作模块走"轻版"——只做 AI 辅助,不做工作流(2026 年 4 月 27 日新增)**

**决定了什么:**

- 写作模块只做"用户输入要点 → AI 生成草稿 → 用户保存/导出"
- 不做"提交 → 书记审阅 → 反馈 → 归档"的工作流

**为什么:**

- 工作流版工程量大,涉及党员档案合规
- 轻版更符合"agent"定位——帮人省力,不替代组织流程
- P0 阶段做轻,留 status 字段未来可扩展

## **决策 2.5:积分系统采用事件溯源模式(2026 年 4 月 27 日新增)**

**决定了什么:**

- 积分用 PointRecord 日志型表记录每次得分,不在 Member 表加 total_points 字段
- 总分由 SUM 算出来

**为什么:**

- 可追溯(每分怎么来的能查到)
- 可撤销(积分错了能扣)
- 可分析(哪类活动得分多)
- 论文里能讲"采用事件溯源(Event Sourcing)模式,保证可审计性"——直接是论文素材

## **决策 2.6:E-R 图 P0 版包含 15 张表(2026 年 4 月 27 日新增)**

**决定了什么:**

P0 版 E-R 图覆盖以下实体:

- 基础(2):Member、Branch
- 学习(5):LearningMaterial、LearningRecord、LearningTask、TaskMaterial、TaskAssignment
- 自测(5):Question、AnswerRecord、Exam、ExamQuestion、ExamAssignment
- 写作(2):WritingTemplate、WritingRecord
- 积分(1):PointRecord

**为什么:**

- 覆盖 P0 三个模块所有实体
- 多对多关系都用关联表实现(TaskMaterial、TaskAssignment、ExamQuestion、ExamAssignment)
- 学习模块和自测模块结构对称,体现设计规律性

**待扩展(P1 阶段加):**

- 会议模块(Meeting、MeetingAttendance、MeetingMinutes 等)
- 发展党员模块(Application、Development、Probation 等)
